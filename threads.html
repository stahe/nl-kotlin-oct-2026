    8. Threads

    Dit hoofdstuk introduceert de gelijktijdige uitvoering van meerdere stukken code binnen één programma: threads (uitvoeringsthreads) en de hulpmiddelen om ze te synchroniseren. Zo'n twintig jaar geleden hadden de meeste machines slechts één processor, en parallellisme was grotendeels een illusie die door het besturingssysteem in stand werd gehouden. Tegenwoordig heeft zelfs de eenvoudigste laptop meerdere cores: meerdere threads worden werkelijk gelijktijdig uitgevoerd, waardoor de hier besproken synchronisatieproblemen nog vaker voorkomen.

    Kotlin heeft op de JVM geen eigen threads: het gebruikt de threads van Java, die vanaf de eerste versie (1996) in Java zijn geïntegreerd via de klasse [Thread], het sleutelwoord [synchronized], en de methoden [wait] en [notify] van de klasse [Object]. Java 5 (2004) voegde het pakket [java.util.concurrent] en de subpakketten [java.util.concurrent.locks] en [java.util.concurrent.atomic] toe: locks, semaforen, concurrente collecties, threadpools enzovoort. Java 7 voegde het framework [Fork/Join] toe, Java 8 introduceerde parallelle streams en Java 21 introduceerde virtuele threads, die allemaal de manier waarop servers worden geschreven ingrijpend hebben veranderd. Java 25 introduceert ten slotte aan een scope gebonden waarden ([ScopedValue]). Al deze klassen uit het JDK-framework zijn rechtstreeks bruikbaar in Kotlin: dit is een van de grote sterke punten ervan. De standaardbibliotheek van Kotlin voegt daar enkele functies aan toe die het gebruik gemakkelijker maken: de functie [thread] en de extensiefunctie [withLock] uit het pakket [kotlin.concurrent], de functie [synchronized] en de annotaties [@Volatile] en [@Synchronized] … We behandelen al deze hulpmiddelen in dit hoofdstuk.

    Threads zijn echter niet het laatste woord van Kotlin over concurrent programmeren: de eigen oplossing voor asynchroniteit zijn coroutines, die in hoofdstuk 9 worden geïntroduceerd. Ze zijn gebaseerd op threads, en alles wat we hier behandelen (kritieke secties, zichtbaarheid van schrijfbewerkingen, deadlocks enzovoort) blijft essentieel om ze volledig te begrijpen.

    De voorbeelden bevinden zich in het Gradle-project [08-threads]. Elk programma is een bestand in een pakket met dezelfde naam ([threads01/Threads01.kt] in het pakket [threads01]…) en wordt uitgevoerd met [gradlew -q run -Pmain=threads01.Threads01Kt], of met de groene driehoek in IntelliJ IDEA. Eventuele programmaargumenten worden aan Gradle doorgegeven met de optie [--args]: [gradlew -q run -Pmain=threads08.Threads08Kt --args="5"].

    Een waarschuwing vooraf: de resultaten van een multithreaded programma verschillen van de ene uitvoering tot de andere. De volgorde waarin threads toegang krijgen tot de processor hangt af van het besturingssysteem, het aantal processors en de belasting van de machine. De in dit hoofdstuk weergegeven resultaten zijn verkregen op een Linux-machine met twee processors die werd gedeeld met andere zeer actieve programma's. Als u de voorbeelden uitvoert, krijgt u vergelijkbare resultaten, maar die zullen zelden identiek zijn. We geven telkens aan wat reproduceerbaar is en wat niet.

    8.1. De klasse Thread

    Wanneer een applicatie wordt gestart, draait ze in een uitvoeringsstroom die een thread wordt genoemd. De klasse die een thread modelleert, is de klasse [java.lang.Thread] in het JDK-pakket. Bedenk dat Kotlin de Java-accessors [getXxx()] / [setXxx(…)] (en [isXxx()] voor een boolean) voorstelt als eigenschappen: we schrijven [thread.name = "Main"] in plaats van [thread.setName("Main")].     De methoden [join] en [sleep] werpen de uitzondering [InterruptedException] als de thread tijdens het wachten wordt onderbroken. In Java is dit een gecontroleerde uitzondering (checked exception), die volgens de compiler moet worden afgehandeld of gedeclareerd in een [throws]-clausule. Kotlin kent geen gecontroleerde uitzonderingen (hoofdstuk 3): de compiler dwingt niets af. Dat betekent niet dat u kunt negeren wat deze uitzondering betekent: daarop komen we terug in de paragraaf over het onderbreken van threads.

    De klasse [Thread] heeft ook een methode [stop], die een thread geforceerd beëindigde. Ze is sinds Java 1.2 verouderd en werpt sinds Java 20 simpelweg de uitzondering [UnsupportedOperationException]: het abrupt stoppen van een thread kon de gegevens die hij verwerkte in een inconsistente toestand achterlaten. Tegenwoordig vragen we een thread om coöperatief te stoppen door hem te onderbreken: daar komen we iets verderop op terug.

package threads01

import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // de thread die deze code uitvoert
    val main = Thread.currentThread()
    // de Java-launcher heeft hem een naam gegeven
    println("Name of the current thread: [${main.name}]")
    // die kan worden gewijzigd
    main.name = "Main"
    println("Name of the current thread: [${main.name}]")
    // enkele properties
    println("Identifier (threadId): ${main.threadId()}")
    println("Daemon thread (isDaemon): ${main.isDaemon}")
    println("Virtual thread (isVirtual): ${main.isVirtual}")
    println("Priority (priority): ${main.priority}")
    println("State (state): ${main.state}")
    println("Text representation: $main")
    println("Number of processors: ${Runtime.getRuntime().availableProcessors()}")

    // een weergave per seconde
    val format = DateTimeFormatter.ofPattern("HH:mm:ss")
    repeat(5) {
        println("${main.name} : ${LocalTime.now().format(format)}")
        // de thread wordt 1 seconde opgeschort
        Thread.sleep(1000)
    }
}

    8.2. Threads aanmaken

    Het is mogelijk applicaties te hebben waarin stukken code „gelijktijdig" in verschillende threads worden uitgevoerd. Als de machine minder processors heeft dan er threads klaar zijn voor uitvoering, delen de threads de processors: elke thread krijgt er om de beurt kortstondig toegang toe (enkele milliseconden). Op een machine met meerdere processors worden meerdere threads werkelijk gelijktijdig uitgevoerd. De tijd die aan een thread wordt toegewezen, hangt van verschillende factoren af, waaronder zijn prioriteit, die een standaardwaarde heeft maar programmatisch kan worden ingesteld (eigenschap [priority]); dit is slechts een richtlijn, die het besturingssysteem mag negeren (Linux negeert haar standaard). Een thread die toegang heeft tot de processor, kan die voortijdig vrijgeven:

    • door op een gebeurtenis te wachten (voltooiing van een andere thread met [join], wachten op een signaal);
    • door gedurende een bepaalde tijd in slaap te gaan ([sleep]).

    Een thread T wordt eerst aangemaakt, bijvoorbeeld met de constructor [Thread(task, name)], waarbij [task] een object is dat de Java-interface [Runnable] implementeert, waarvan de enige methode [void run()] is. Dankzij de SAM-conversie die in hoofdstuk 7 is beschreven, wordt er in plaats van een lambda of een functiereferentie van het type [() -> Unit] doorgegeven in plaats van een [Runnable]. In oudere code komen we ook klassen tegen die zijn afgeleid van [Thread] en de methode [run] opnieuw definiëren: dit wordt niet aanbevolen, omdat het de uit te voeren taak vermengt met de manier waarop ze wordt uitgevoerd.

    Een thread aanmaken start hem niet:

    • de uitvoering van thread T wordt gestart met [T.start()]: de methode [run] van de taak die aan de constructor van T is doorgegeven, wordt dan door thread T uitgevoerd. De code die de instructie [T.start()] uitvoert, wacht niet tot thread T klaar is: ze gaat onmiddellijk door met de volgende instructie. We hebben nu twee threads die parallel draaien. Ze moeten vaak met elkaar communiceren om de voortgang van het gedeelde werk te volgen: dit is het probleem van de synchronisatie van threads;
    • Eenmaal gestart draait thread T zelfstandig. Hij stopt wanneer de functie die hij uitvoert is voltooid;
    • we kunnen wachten tot hij klaar is met uitvoeren met [T.join()]. Dit is een blokkerende instructie: de thread die haar uitvoert, is geblokkeerd totdat thread T zijn werk heeft voltooid. Dit is een elementaire synchronisatiemethode.

package threads02

import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // de hoofdthread heeft een naam
    Thread.currentThread().name = "Main"

    // aanmaken van 5 threads
    val tasks = Array(5) { i ->
        // thread nr. i voert de functie display uit; hij krijgt de naam "i"
        Thread(::display, i.toString())
    }
    // hun uitvoering wordt gestart (niet-blokkerende bewerking)
    for (task in tasks) {
        task.start()
    }

    // einde van de hoofdthread
    println("End of thread ${Thread.currentThread().name} at ${time()}")
}

// de functie die door de threads wordt uitgevoerd: ze heeft de vorm van Runnable.run()
fun display() {
    // de thread die de functie uitvoert
    val current = Thread.currentThread()
    println("Start of execution of the display function in thread ${current.name}" +
            " (id ${current.threadId()}) : ${time()}")
    // 1 s slapen
    sleep(1000)
    println("End of execution of the display function in thread ${current.name} : ${time()}")
}

// [ms] milliseconden slapen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        // het slapen is onderbroken: de interrupt-vlag van de thread wordt hersteld
        Thread.currentThread().interrupt()
    }
}

// de huidige tijd, tot op de milliseconde
fun time(): String = LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"))

    Opmerkingen:

    • regel 9: de hoofdthread krijgt een naam;
    • regels 12–14: er worden 5 threads aangemaakt. De functie [Array(5) { i -> … }] maakt een array van 5 elementen aan, waarbij element i de waarde is die door de lambda wordt geretourneerd. De verwijzingen naar de threads worden dus in een array opgeslagen zodat ze later kunnen worden opgehaald. Elke thread voert de functie [display] uit op regels 26–33;
    • Regel 14: de functiereferentie [::display], van het type [() -> Unit], wordt automatisch omgezet naar een object [Runnable]: de functie [display] heeft geen parameters en retourneert geen resultaat, net als [run]. In Java had u in een compact bronbestand [this::display] moeten schrijven; in Kotlin is [display] een functie op het hoogste niveau, waarnaar eenvoudigweg wordt verwezen als [::display]. De tweede parameter van de constructor is de naam van de thread;
    • regels 17–18: de threads worden gestart. Deze bewerking is niet-blokkerend: thread nr. i draait parallel aan de hoofdthread die hem heeft gestart;
    • regel 22: de hoofdthread bereikt het einde van het programma;
    • regels 26–33: de functie [display] toont de naam en het ID van de thread die haar uitvoert, evenals de begin- en eindtijd (tot op de milliseconde) van de uitvoering;
    • regel 32: elke thread die de functie [display] uitvoert, pauzeert 1 seconde. De processor wordt dan overgedragen aan een andere thread die op de processor wacht. Aan het einde van de pauze van 1 seconde komt de gepauzeerde thread weer in aanmerking voor de processor. Hij krijgt hem wanneer hij aan de beurt is;
    • Regels 37–42: de functie [sleep] omhult [Thread.sleep]. De Kotlin-compiler eist niet dat de uitzondering [InterruptedException] die [sleep] kan werpen, wordt afgevangen. Als ze echter uit de functie van een thread zou ontsnappen, zou ze die thread beëindigen met een foutmelding op de console. De functie [sleep] vangt haar daarom af en zet de onderbrekingsvlag van de thread terug (regel 42); we lichten deze handeling toe in de paragraaf over onderbrekingen. De naam [_] die aan de parameter van de clausule [catch] is gegeven, geeft aan dat deze parameter niet wordt gebruikt. We komen deze kleine functie tegen in de meeste programma's van dit hoofdstuk;
    • regel 47: de functie [time], geschreven als expressie ([= …]), retourneert de huidige tijd in de notatie [HH:mm:ss.SSS] ([SSS]: milliseconden).

package threads03

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.concurrent.thread

fun main() {
    // de hoofdthread heeft een naam
    Thread.currentThread().name = "Main"

    // aanmaken en starten van 5 daemon-threads met de namen 0, 1, 2…
    for (i in 0..<5) {
        // thread maakt een thread aan, configureert hem en start hem (standaard) onmiddellijk
        thread(isDaemon = true, name = "$i") {
            display()
        }
    }

    // de threads krijgen de tijd om te starten
    sleep(100)
    // einde van de hoofdthread, dus van het programma
    println("End of thread ${Thread.currentThread().name} at ${time()}")
}

// de functie die door de threads wordt uitgevoerd
fun display() {
    val current = Thread.currentThread()
    println("Start of execution of the display function in thread ${current.name} : ${time()}")
    // 1 s slapen
    sleep(1000)
    println("End of execution of the display function in thread ${current.name} : ${time()}")
}

// [ms] milliseconden slapen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }

    8.3. Een thread stoppen: onderbreking

    Hoe stopt u een thread voordat hij zijn werk heeft voltooid, bijvoorbeeld wanneer de gebruiker een langdurige bewerking annuleert? De JVM staat niet toe dat u een thread doodt; ze biedt een coöperatief mechanisme dat onderbreking heet:

    • Elke thread heeft een onderbrekingsvlag, een Boolean die aanvankelijk op [false] staat;
    • Een thread met de naam T1 die de thread T2 wil beëindigen, roept [T2.interrupt()] aan. Hierdoor wordt de beëindigingsvlag van T2 gezet. Dit is een verzoek tot beëindiging: T2 wordt niet beëindigd; die thread moet zelf beslissen wanneer en hoe hij eindigt, zodat zijn gegevens in een consistente toestand blijven;
    • als T2 geblokkeerd is in een wachtmethode ([sleep], [join], [wait] en de meeste blokkerende methoden in [java.util.concurrent]), wordt hij gewekt: de methode werpt de uitzondering [InterruptedException], en de onderbrekingsvlag wordt teruggezet op [false];
    • als T2 berekeningen uitvoert zonder ooit te wachten, moet de thread met regelmatige tussenpozen zijn eigen vlag controleren met [Thread.currentThread().isInterrupted] .

    In Java declareren blokkerende methoden de gecontroleerde exception [InterruptedException]: de compiler verplicht de programmeur te beslissen wat er met een stopverzoek gebeurt. Kotlin eist dit niet, maar de beslissing moet toch worden genomen, en die is dezelfde. Er zijn twee juiste reacties: de exception laten doorlopen naar de aanroeper, of de exception afvangen en de taak netjes afronden. Wanneer geen van beide mogelijk is, zoals in de functie [sleep] van het programma [Threads02.kt], wordt de vlag opnieuw gezet met [Thread.currentThread().interrupt()] zodat de aanroepende code het verzoek alsnog kan zien. package threads05

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // 1 - een thread die het grootste deel van de tijd slaapt
    val sleeper = Thread.ofPlatform().name("sleeper").start {
        var round = 0
        try {
            while (true) {
                round++
                println("${time()} : sleeper, round $round")
                // sleep genereert InterruptedException als de thread tijdens het slapen wordt onderbroken
                Thread.sleep(400)
            }
        } catch (_: InterruptedException) {
            // de onderbreking is een verzoek om te stoppen: de thread rondt zijn werk netjes af
            println("${time()} : sleeper interrupted while sleeping, it stops")
        }
    }
    // 2 - een thread die rekent zonder ooit te slapen
    val calculator = Thread.ofPlatform().name("calculator").start {
        var n = 0L
        // de thread controleert regelmatig zijn interrupt-vlag
        while (!Thread.currentThread().isInterrupted) {
            n++
        }
        println("${time()} : calculator interrupted after %,d iterations, it stops".format(n))
    }
    // 3 - een thread die onderbrekingen negeert (niet om na te volgen)
    val deaf = Thread.ofPlatform().name("deaf").daemon().start {
        repeat(10) {
            try {
                Thread.sleep(400)
            } catch (_: InterruptedException) {
                // de exception wordt "ingeslikt": het verzoek om te stoppen gaat verloren
                println("${time()} : deaf ignores the interruption and continues")
            }
        }
    }

    // de threads mogen 1 s werken
    Thread.sleep(1000)
    println("${time()} : Main requests the three threads to stop")
    sleeper.interrupt()
    calculator.interrupt()
    deaf.interrupt()
    // wachten op het einde van elke thread, maximaal 1 s
    for (thread in listOf(sleeper, calculator, deaf)) {
        val finished = thread.join(Duration.ofSeconds(1))
        println("${time()} : thread ${thread.name} finished: $finished")
    }
}

    8.4. Virtuele threads

    De threads die we tot nu toe hebben gemaakt, zijn platformthreads: elk daarvan is een omhulsel rond een thread van het besturingssysteem, die het gedurende zijn hele levensduur bezet. Een thread van het besturingssysteem is een kostbare resource: het aanmaken kost tijd, de stack reserveert geheugen (in de orde van een megabyte) en het systeem kan er niet efficiënt meer dan een paar duizend beheren. Een server die voor elke client een thread reserveert (zie het schema in de volgende paragraaf) brengt echter het grootste deel van zijn tijd wachtend door: op een antwoord van een database, op het volgende verzoek van de client… Tijdens deze wachttijden is de systeemthread geblokkeerd en onbruikbaar.

    Java 21 introduceerde virtuele threads (JEP 444), die in Kotlin zonder meer bruikbaar zijn. Een virtuele thread is een [Thread]-object zoals elk ander, maar wordt beheerd door de Java Virtual Machine in plaats van door het besturingssysteem:

    • om uitgevoerd te worden, wordt een virtuele thread gekoppeld aan een platformthread, de „carrier thread” genoemd. Carrier threads vormen een kleine pool, waarvan de grootte standaard gelijk is aan het aantal processors;
    • wanneer een virtuele thread blokkeert ([sleep], wachten op netwerk-I/O, een lock, een blokkerende wachtrij enzovoort), wordt hij ontkoppeld: zijn stack wordt opzijgezet in het geheugen van de virtuele machine en de carrier thread is meteen beschikbaar voor een andere virtuele thread. Wanneer het wachten voorbij is, wordt de virtuele thread weer aan een carrier thread gekoppeld—niet noodzakelijk dezelfde;
    • een virtuele thread neemt enkele honderden bytes in beslag: er kunnen miljoenen worden aangemaakt.

    De coroutines van Kotlin (hoofdstuk 9) berusten op een vergelijkbaar idee—een wachtend proces opschorten zonder een systeemthread te blokkeren—maar worden geïmplementeerd door de Kotlin-compiler in plaats van door de virtuele machine. We vergelijken beide benaderingen in hoofdstuk 9.

    8.5. Het nut van threads

    Nu we hebben laten zien dat er een standaardthread bestaat—die de functie [main] uitvoert—en we weten hoe we extra threads maken, bekijken we het nut van threads wat nauwkeuriger. Er zijn twee hoofdtoepassingen:

    • om alle processors van de machine te benutten voor een tijdrovende berekening: het werk wordt opgedeeld in stukken die aan verschillende threads worden toegewezen. Dat doen we aan het eind van dit hoofdstuk met parallelle streams en het [Fork/Join]-raamwerk;
    • om meerdere taken tegelijk uit te voeren, vooral wanneer sommige daarvan hoofdzakelijk bestaan uit wachten (op een netwerkantwoord, een leesactie van schijf of invoer van de gebruiker). Dit is het geval bij client-serverapplicaties op internet, die we in hoofdstuk 12 behandelen.

    In een client-serverapplicatie op internet beantwoordt een server op een machine S1 verzoeken van clients op externe machines C1, C2, …, Cn:

    We gebruiken dagelijks internettoepassingen die dit patroon volgen: webservices, e-mail, bestandsoverdracht enzovoort. In het schema hierboven moet de server S1 de clients Ci gelijktijdig bedienen. Neem als voorbeeld een bestandsserver: we weten dat een overdracht soms enkele minuten kan duren. Het is uitgesloten dat één client de server zo lang monopoliseert. Een gangbare oplossing is dat de server evenveel uitvoeringsthreads aanmaakt als er clients zijn.     Bij platformthreads gebruikt de server in feite een threadpool—dat later aan bod komt—waarvan het beperkte aantal threads het aantal gelijktijdig bediende clients begrenst. Met virtuele threads is het bovenstaande schema opnieuw de optimale oplossing: één virtuele thread per client, zelfs bij tienduizenden clients, omdat een wachtende client geen systeemthreads bezet. Dit wordt nu ondersteund door JVM-webservers zoals Tomcat—die we in hoofdstuk 13 gebruiken. In Kotlin bieden de coroutines uit hoofdstuk 9 een andere oplossing voor ditzelfde probleem: één coroutine per client.

package threads07

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.concurrent.thread

// de informatie die wordt uitgewisseld tussen de startende thread en de gestarte thread
class Data(
    // ingesteld door de startende thread
    val start: LocalTime,
    val duration: Int,
) {
    // ingesteld door de gestarte thread
    lateinit var end: LocalTime
}

fun main() {
    // de hoofdthread heeft een naam
    Thread.currentThread().name = "Main"

    // aanmaken en starten van 5 threads
    val data = mutableListOf<Data>()
    val tasks = mutableListOf<Thread>()
    for (i in 0..<5) {
        // het object dat met de thread wordt uitgewisseld: de startende thread stelt het begin en de duur in
        val d = Data(LocalTime.now(), i + 1)
        data += d
        // de gestarte thread ontvangt het object via de lambda die het vastlegt
        tasks += thread(name = "$i") { sleep(d) }
    }

    // we wachten na elkaar op de threads
    val format = DateTimeFormatter.ofPattern("HH:mm:ss")
    for ((task, d) in tasks.zip(data)) {
        // wachten op het einde van de thread
        task.join()
        // de thread heeft de eindtijd van zijn object ingevuld
        val actualDuration = Duration.between(d.start, d.end).toMillis() / 1000.0
        println("Thread %s finished: start %s, scheduled duration %d s, end %s, actual duration %.3f s"
            .format(task.name, d.start.format(format), d.duration, d.end.format(format), actualDuration))
    }
    // einde van de hoofdthread
    println("End of thread ${Thread.currentThread().name} at ${LocalTime.now().format(format)}")
}

// de functie die door de threads wordt uitgevoerd
fun sleep(data: Data) {
    try {
        // [duration] seconden slapen
        Thread.sleep(data.duration * 1000L)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
    // de gestarte thread geeft een resultaat terug aan de startende thread
    data.end = LocalTime.now()
}

    8.7.2. De functie synchronized en de annotatie @Synchronized

    In Java begrenst het blok [synchronized] een kritieke sectie als volgt: [synchronized (lock) { …critical section… }]. [lock] is een object dat zichtbaar is voor alle threads die de kritieke sectie uitvoeren. Op de JVM heeft elk object een interne lock, ook wel monitor genoemd. Het blok [synchronized] zorgt ervoor dat slechts één thread tegelijk de monitor van het object [lock] vasthoudt, zodat slechts één thread tegelijk de kritieke sectie uitvoert: een thread die een monitor aantreft die door een andere thread wordt vastgehouden, wordt geblokkeerd totdat de monitor is vrijgegeven. De monitor wordt vrijgegeven bij het verlaten van het blok, zowel bij een normale uitgang als bij een exception.

    Kotlin kent geen sleutelwoord [synchronized]. In plaats daarvan biedt de standaardbibliotheek een [synchronized]-functie, met de signatuur [inline fun <R> synchronized(lock: Any, block: () -> R): R]. Dankzij de syntaxis van de laatste lambda wordt de aanroep [synchronized(lock) { …critical section… }] precies zo geschreven als het Java-blok. Omdat de functie [inline] is, vervangt de Kotlin-compiler de aanroep door de body van de lambda, omgeven door dezelfde instructies als bij de JVM, net als bij het Java-blok ([monitorenter] / [monitorexit]): er is geen verschil in uitvoering. De functie geeft de waarde van de lambda terug, zodat we [val v = synchronized(lock) { counter }] kunnen schrijven.

package threads10

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.system.exitProcess

// de gedeelde resource
object Counter {
    // de threadteller
    private var counter = 0
    // het synchronisatieobject, zichtbaar voor alle threads
    private val lock = Any()

    // de waarde van de teller, gelezen onder bescherming van de lock
    val value: Int
        get() = synchronized(lock) { counter }

    // de functie die door elke thread wordt uitgevoerd
    fun increment() {
        val name = Thread.currentThread().name
        println("At ${time()}, thread $name is waiting for permission to enter the critical section")
        // slechts één thread tegelijk voert het volgende blok uit
        synchronized(lock) {
            // de teller lezen
            val v = counter
            println("At ${time()}, thread $name read the counter value: $v")
            // wachten: de thread verliest de processor maar behoudt de lock
            sleep(1000)
            // de teller ophogen
            counter = v + 1
            println("At ${time()}, thread $name wrote the counter value: $counter")
        }
        println("At ${time()}, thread $name left the critical section")
    }
}

    8.7.4. Processen synchroniseren: de bestandslock

    De vorige locks synchroniseren threads binnen dezelfde virtuele machine—dus binnen hetzelfde proces. Soms moeten verschillende processen een resource delen, zoals een bestand, of wilt u voorkomen dat twee instanties van dezelfde applicatie worden gestart. De JVM biedt geen benoemd synchronisatieobject dat tussen processen wordt gedeeld; hiervoor gebruikt men een bestandslock die door het besturingssysteem wordt beheerd: de klasse [java.nio.channels.FileLock]. Een lock wordt verkregen op een geopend bestand in de vorm van een kanaal [FileChannel]:

    • [lock(): FileLock]: wacht tot de lock beschikbaar is en verkrijgt hem;
    • [tryLock(): FileLock?]: probeert de lock te verkrijgen zonder te wachten en geeft [null] terug als een ander proces hem vasthoudt. Kotlin behandelt de retourwaarde van deze Java-methode als een platformtype ([FileLock!]); het is aan de programmeur om die waarde te behandelen als een waarde die mogelijk [null] is;
    • [release()]: geeft de lock vrij. De lock wordt ook vrijgegeven wanneer het kanaal wordt gesloten of het proces eindigt, zelfs als het abrupt wordt beëindigd: een lock kan niet „verweesd” achterblijven. De klasse [FileLock] implementeert de interface [AutoCloseable]: de methode [close] roept [release] aan, en de Kotlin-functie [use] kan de lock dus vrijgeven.

import java.util.concurrent.Semaphore

// de gedeelde resource
object Counter {
    // de threadteller
    var value = 0
        private set
    // de barrière: een semafoor die zonder permit is aangemaakt, dus gesloten
    val sync = Semaphore(0)

    // de functie die door elke thread wordt uitgevoerd
    fun increment() {
        val name = Thread.currentThread().name
        println("At ${time()}, thread $name is waiting for permission to enter the critical section")
        // de barrière passeren: de thread neemt de enige permit, de barrière sluit achter hem
        sync.acquireUninterruptibly()
        try {
            // de teller lezen
            val v = value
            println("At ${time()}, thread $name read the counter value: $v")
            // wachten
            sleep(1000)
            // de teller ophogen
            value = v + 1
            println("At ${time()}, thread $name wrote the counter value: $value")
        } finally {
            // de permit wordt teruggegeven: de barrière gaat open voor een andere thread
            println("At ${time()}, thread $name leaves the critical section")
            sync.release()
        }
    }
}

        exitProcess(1)

    val threads = List(nbThreads) { i -> Thread(Counter::increment, "$i") }
    threads.forEach { it.start() }

    8.7.7. Zichtbaarheid van schrijfacties: de annotatie @Volatile

    Locks dienen niet alleen om een groep bewerkingen ondeelbaar te maken. Ze lossen een tweede, verraderlijker probleem op: de zichtbaarheid van schrijfacties. Om de uitvoering te versnellen, slaat de processor waarden op in zijn registers en caches, en wijzigt de compiler on the fly de volgorde van lees- en schrijfacties of laat hij ze weg, zoals we zagen bij het programma [Threads09.kt]. Het gevolg is dat een waarde die door de ene thread is geschreven, pas later door een andere thread te zien is—of misschien helemaal nooit.

    Het Java-geheugenmodel , dat alle programma’s regelt die door de JVM worden uitgevoerd—ook Kotlin-programma’s—definieert nauwkeurig wanneer een schrijfactie gegarandeerd zichtbaar is: wanneer er een „happens-before”-relatie bestaat tussen de schrijfactie en de leesactie. De belangrijkste zijn de volgende:

    • alles wat een thread heeft gedaan voordat hij een lock vrijgeeft (einde van een blok [synchronized], [unlock]), is zichtbaar voor de thread die vervolgens die lock verkrijgt;
    • wat de aanroepende thread vóór [start] heeft gedaan, is zichtbaar voor de aangeroepen thread; wat een thread heeft gedaan, is zichtbaar voor de thread die via [join] op het einde ervan heeft gewacht;
    • een schrijfactie naar een veld [volatile] is zichtbaar voor elke latere leesactie van dat veld;
    • de hulpmiddelen in [java.util.concurrent] bieden vergelijkbare garanties: wat een thread heeft gedaan vóór [release()], [countDown()], of vóór het invoegen van een element in een concurrent collection, is zichtbaar voor de thread die vervolgens [acquire()], [await()], uitvoert of het element ophaalt.

    Wanneer geen van deze relaties bestaat, bevat het programma naar men zegt een „data race” en zijn er geen garanties. In Java wordt een veld met een sleutelwoord [volatile] gedeclareerd; Kotlin kent dit sleutelwoord niet, maar heeft wel een annotatie, [@Volatile], die wordt toegepast op een property [var]: het veld dat de property opslaat, is dan een Java-veld [volatile]. package threads16

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter

// de stopvlaggen, gedeeld door de threads
object Flags {
    // een gewone property: een thread ziet de nieuwe waarde mogelijk nooit
    var stop = false
    // een volatile property: elke schrijfactie is zichtbaar voor de leesacties die erop volgen
    @Volatile
    var volatileStop = false
}

fun main() {
    // 1 - de stopvlag is een gewone property
    val t1 = Thread.ofPlatform().name("T1").daemon().start {
        var rounds = 0L
        while (!Flags.stop) {
            rounds++
        }
        println("${time()} : T1 saw the stop request after %,d rounds".format(rounds))
    }
    // 2 - de stopvlag is een volatile property
    val t2 = Thread.ofPlatform().name("T2").daemon().start {
        var rounds = 0L
        while (!Flags.volatileStop) {
            rounds++
        }
        println("${time()} : T2 saw the stop request after %,d rounds".format(rounds))
    }

    // de threads blijven één seconde draaien
    Thread.sleep(1000)
    println("${time()} : Main requests T1 and T2 to stop")

    Flags.volatileStop = true
    // wachten op het einde van de twee threads, maximaal 2 s elk
    for (thread in listOf(t2, t1)) {
        val finished = thread.join(Duration.ofSeconds(2))
        println("${time()} : ${thread.name} finished: $finished")

    8.7.8. Atomaire klassen

    Het pakket [java.util.concurrent.atomic] (Java 5) biedt klassen die eenvoudige bewerkingen op een variabele atomair maken: de bewerking wordt in zijn geheel door de thread uitgevoerd, zonder dat een andere thread de variabele halverwege de bewerking kan waarnemen of wijzigen.     // @Volatile garandeert de zichtbaarheid van schrijfacties, niet de atomiciteit van value++
    @Volatile
    var value = 0
    private val lock = Any()
    private val reentrantLock = ReentrantLock()
    val atomic = AtomicInteger()
    val adder = LongAdder()

    // reset van de tellers
    fun reset() {
        value = 0
        atomic.set(0)
        adder.reset()
    }

    // lezen, ophogen, schrijven: niet atomair
    fun withoutSynchronization() {
        value++
    }

    // kritieke sectie beschermd door synchronized
    fun withSynchronized() {
        synchronized(lock) {
            value++
        }
    }

    // synchronized-functie: de lock is het Counter-object zelf
    @Synchronized
    fun withSynchronizedAnnotation() {
        value++
    }

    // kritieke sectie beschermd door een ReentrantLock
    fun withReentrantLock() {
        reentrantLock.withLock {
            value++
        }
    }

    // atomaire verhoging, zonder lock
    fun withAtomicInteger() {
        atomic.incrementAndGet()
    }

    // verhoging van een gedistribueerde adder, zonder lock
    fun withLongAdder() {
        adder.increment()
    }
}

fun main(args: Array<String>) {
    // parameters: aantal threads, aantal ophogingen per thread
    val nbThreads = args.getOrNull(0)?.toInt() ?: 4
    val nbIncrements = args.getOrNull(1)?.toInt() ?: 10_000_000
    println("%d threads, %,d increments per thread, expected value %,d"
        .format(nbThreads, nbIncrements, nbThreads * nbIncrements))

    // zes manieren om een gedeelde teller te verhogen
    val value = { Counter.value.toLong() }
    measure("without synchronization", nbThreads, nbIncrements, Counter::withoutSynchronization, value)
    measure("with synchronized", nbThreads, nbIncrements, Counter::withSynchronized, value)
    measure("with @Synchronized", nbThreads, nbIncrements, Counter::withSynchronizedAnnotation, value)
    measure("with ReentrantLock", nbThreads, nbIncrements, Counter::withReentrantLock, value)
    measure("with AtomicInteger", nbThreads, nbIncrements, Counter::withAtomicInteger) {
        Counter.atomic.get().toLong()
    }
    measure("with LongAdder", nbThreads, nbIncrements, Counter::withLongAdder, Counter.adder::sum)
}

// start de threads die allemaal [increment] nbIncrements keer uitvoeren en toont daarna [value]
fun measure(method: String, nbThreads: Int, nbIncrements: Int, increment: () -> Unit, value: () -> Long) {
    Counter.reset()
    // een startsignaal zodat alle threads tegelijk beginnen
    val startSignal = CountDownLatch(1)
    val threads = List(nbThreads) {
        Thread.ofPlatform().start {
            try {
                startSignal.await()
            } catch (_: InterruptedException) {
                return@start
            }
            repeat(nbIncrements) { increment() }
        }
    }
    // go!
    val begin = System.nanoTime()
    startSignal.countDown()
    threads.forEach { it.join() }
    val duration = (System.nanoTime() - begin) / 1_000_000
    println("%-23s : value obtained %,12d in %5d ms".format(method, value(), duration))
}

    8.8. Gelijktijdige toegang tot meerdere gedeelde resources

    8.8.1. Deadlock

    In onze vorige voorbeelden werd één resource door de verschillende threads gedeeld. De situatie wordt ingewikkelder als er meerdere resources zijn die van elkaar afhankelijk zijn. Er kan met name een deadlock ontstaan: twee threads wachten op elkaar. Beschouw de volgende acties, die achtereenvolgens plaatsvinden:

    • een thread T1 verkrijgt de lock V1 om toegang te krijgen tot een gedeelde resource R1;
    • een thread T2 verkrijgt de lock V2 om toegang te krijgen tot een gedeelde resource R2;
    • thread T1 vraagt lock V2 aan. Die thread wordt geblokkeerd;
    • de thread T2 vraagt de lock V1 aan. Die thread wordt geblokkeerd.

    De threads T1 en T2 wachten onbeperkt op elkaar. Er zijn verschillende oplossingen mogelijk:

    • beide resources tegelijk aanvragen met één enkele lock. Dit is niet altijd mogelijk als daardoor een kostbare resource lang wordt vergrendeld;
    • altijd locks verkrijgen in dezelfde volgorde: als alle threads V1 voor V2 verkrijgen, is een deadlock onmogelijk. Dit is de meest gebruikte regel;
    • een thread die V1 vasthoudt en V2 niet kan verkrijgen, geeft V1 vrij om een deadlock te voorkomen.

fun main() {
    // de locks van de twee gedeelde resources
    val lockR1 = ReentrantLock()
    val lockR2 = ReentrantLock()

    // T1 neemt R1 en vraagt dan R2 aan; hij geeft het na 2 s op
    val t1 = thread(name = "T1") { work(lockR1, "R1", lockR2, "R2", 2.seconds) }
    // T2 neemt R2 en vraagt dan R1 aan; hij wacht maximaal 5 s
    val t2 = thread(name = "T2") { work(lockR2, "R2", lockR1, "R1", 5.seconds) }
    t1.join()
    t2.join()
    println("End of Main")
}

// neemt de 1e resource en probeert vervolgens de 2e te nemen gedurende [timeout]
fun work(first: Lock, firstName: String, second: Lock, secondName: String, timeout: Duration) {
    val name = Thread.currentThread().name
    first.withLock {
        println("${time()} : $name obtained $firstName")
        try {
            // de andere thread krijgt de tijd om zijn eerste resource te nemen
            Thread.sleep(500)
            println("${time()} : $name requests $secondName")
            // aanvraag met een maximale wachttijd, in plaats van een lock() die onbeperkt zou wachten
            if (second.tryLock(timeout.inWholeMilliseconds, TimeUnit.MILLISECONDS)) {
                try {
                    println("${time()} : $name obtained $secondName" +
                            " and works with $firstName and $secondName")
                } finally {
                    second.unlock()
                }
            } else {
                println("${time()} : $name did not obtain $secondName in ${timeout.inWholeSeconds} s:" +
                        " it releases $firstName and gives up")
            }
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }
}

    8.8.2. Een voorbeeld: lezers en schrijvers

    Beschouw het volgende voorbeeld:

    • We hebben een array waarin sommige threads gegevens schrijven (de schrijvers) en andere die lezen (de lezers);
    • de schrijvers zijn aan elkaar gelijk maar sluiten elkaar uit: slechts één schrijver tegelijk kan gegevens in de array plaatsen;
    • de lezers zijn aan elkaar gelijk maar sluiten elkaar uit: slechts één lezer tegelijk kan de in de array opgeslagen gegevens lezen;
    • een lezer kan alleen gegevens uit de array lezen als een schrijver er gegevens in heeft geplaatst, en een schrijver kan alleen nieuwe gegevens in de array plaatsen als de reeds aanwezige gegevens door een lezer zijn gelezen.

    Er zijn twee soorten gedeelde resources:

    • de beschrijfbare tabel: slechts één schrijver tegelijk heeft er toegang toe;
    • de leesbare tabel: slechts één lezer tegelijk heeft er toegang toe.

    en een volgorde voor het gebruik van deze resources:

    • een lezer moet altijd op een schrijver volgen;
    • een schrijver moet altijd op een lezer volgen, behalve de eerste keer.

    De toegang tot deze twee resources kan worden geregeld met twee barrières van het type [Semaphore]:

    • de barrière [canWrite] regelt de toegang van de schrijvers tot de array;
    • de barrière [canRead] regelt de toegang van de lezers tot de array;
    • de barrière [canWrite] wordt in open toestand aangemaakt (één permit), waardoor de eerste schrijver erdoor kan en alle andere worden geblokkeerd;
    • de barrière [canRead] wordt in gesloten toestand aangemaakt (geen permit), waardoor alle lezers worden geblokkeerd;
    • wanneer een schrijver zijn werk heeft afgerond, opent hij de barrière [canRead] om een lezer binnen te laten;
    • wanneer een lezer zijn werk heeft afgerond, opent hij de barrière [canWrite] om een schrijver binnen te laten.

    Hier zien we het voordeel van een barrière die aan geen enkele thread toebehoort: de barrière [canRead] wordt gesloten door een lezer (die de toestemming neemt) en geopend door een schrijver (die haar teruggeeft).     // aanmaken en starten van de schrijfthreads

    println("End of Main...")

// de gedeelde resource en de synchronisatie ervan
object Board {
    // de array die door lezers en schrijvers wordt gedeeld
    private val data = IntArray(3)
    // meldt dat de inhoud van data kan worden gelezen: aan het begin gesloten (geen permit)
    private val canRead = Semaphore(0)
    // meldt dat data kan worden geschreven: aan het begin open (één permit)
    private val canWrite = Semaphore(1)

    // de inhoud van de array lezen
    fun read() {
        val name = Thread.currentThread().name
        println("Function [read] started by thread $name")
        // we wachten op leestoestemming
        canRead.acquireUninterruptibly()
        // de array lezen
        for (number in data) {
            // wachttijd van 0,5 s: de thread verliest de processor
            sleep(500)
            println("${time()} : reader $name read the number $number")
        }
        // een schrijver krijgt toestemming
        canWrite.release()
        println("Function [read] finished by thread $name")
    }

    // naar de array schrijven
    fun write() {
        val name = Thread.currentThread().name
        println("Function [write] started by thread $name")
        // we wachten op schrijftoestemming
        canWrite.acquireUninterruptibly()
        // de array schrijven
        for (i in data.indices) {
            // wachttijd van 0,5 s
            sleep(500)
            // een willekeurig getal in het interval [0, 1000[
            data[i] = Random.nextInt(0, 1000)
            println("${time()} : writer $name wrote the number ${data[i]}")
        }
        // een lezer krijgt toestemming
        canRead.release()
        println("Function [write] finished by thread $name")
    }
}

    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }

    8.8.3. De methoden wait en notifyAll

    In het vorige voorbeeld wordt, wanneer schrijvers geblokkeerd zijn op de instructie [canWrite.acquireUninterruptibly()], een van hen – willekeurig welke – gedeblokkeerd door de bewerking [canWrite.release()]. Wilt u de barrière voor een bepaalde schrijver openen, dan wordt het ingewikkelder.

    Denk aan de analogie van een publieke dienst met loketten. Wanneer een klant binnenkomt, neemt hij een volgnummer uit de automaat en gaat hij zitten. Klanten worden via een luidspreker op nummer afgeroepen. Tijdens het wachten kan de klant doen wat hij wil: lezen of indommelen. Telkens wanneer de luidspreker een nummer omroept, wordt hij wakker. Is het zijn nummer, dan staat de klant op en gaat hij naar het loket; zo niet, dan gaat hij verder met waar hij mee bezig was. Met threads kunnen we op vergelijkbare wijze te werk gaan. Laten we het voorbeeld van de schrijvers nemen:

Dat doen we hieronder eenmalig, in de declaratie van het token: het type ervan is dan [java.lang.Object], en de aanroepen [token.wait()] en [token.notifyAll()] leiden niet meer tot een waarschuwing. Dit kleine ongemak is opzettelijk: in Kotlin geven we de voorkeur aan de interface [Condition], die in de volgende paragraaf wordt behandeld. Het is niettemin nuttig vertrouwd te zijn met [wait] en [notifyAll], die in veel bestaande Java-code voorkomen.

    We beschrijven nu een standaardpatroon – dat onder meer wordt gepresenteerd in het boek van Brian Goetz et al., [Java Concurrency in Practice] – waarmee barrièreproblemen met toegangsvoorwaarden kunnen worden opgelost.

    Threads die een bron (het loket) delen, benaderen die via een object dat we een token noemen: het is een eenvoudig object ([Object()]) waarvan de monitor wordt gebruikt. Om de barrière naar het loket te passeren, moet men het token hebben, en er is er maar één. De threads moeten het token dus aan elkaar doorgeven.

    Om naar het loket te gaan, vraagt een thread eerst het token aan met een blok [synchronized(token) { … }]. Verkrijgt hij het token, dan controleert hij in een lus [while (!iAmTheExpectedOne) { token.wait() }] of hij voldoet aan de voorwaarde om naar het loket te gaan, en gaat vervolgens naar het loket, nog steeds binnen het blok [synchronized]. Is de thread niet degene die bij het loket wordt verwacht, dan geeft hij zijn beurt op door het token terug te geven via [token.wait()] en gaat hij naar de geblokkeerde toestand. Hij wordt wakker gemaakt wanneer een andere thread een wijziging in de toegangsvoorwaarde meldt; hij krijgt dan het token terug en controleert de voorwaarde opnieuw. Daarom is de test een lus ([while]) en geen eenvoudige [if]. Er is een tweede reden, die specifiek is voor de JVM: de specificatie staat „spurious wakeups” toe, waarbij [wait] eindigt zonder dat een thread [notify] heeft aangeroepen; de lus maakt ze onschadelijk. De bewerking [token.wait()] kan alleen worden uitgevoerd door een thread die de monitor van het token bezit; anders wordt een [IllegalMonitorStateException]-uitzondering opgeworpen. In dit schema wordt het token pas vrijgegeven nadat de transactie is voltooid.

    De thread die de voorwaarde voor toegang tot het loket wijzigt, moet eveneens het token bezitten en de wachtende threads waarschuwen: binnen een blok [synchronized(token) { … }] wijzigt hij de toegangsvoorwaarde en maakt hij vervolgens de wachtende threads wakker met [token.notifyAll()].

    Het wakker maken van de threads betekent dat de wachtende threads kandidaat worden voor het token; zij ontvangen het niet onmiddellijk. Het token is pas beschikbaar aan het einde van het blok [synchronized]. Alle wakker gemaakte threads ontvangen het token vervolgens om beurten, in onbepaalde volgorde, waardoor zij de toegangsvoorwaarde opnieuw kunnen controleren. De eerste die aan de voorwaarde voldoet, houdt het token en gaat naar het loket.

// de gedeelde resource en de synchronisatie ervan
object Board {
    // de array die door lezers en schrijvers wordt gedeeld
    private val data = IntArray(3)
    // de toegangstokens van de lees- en schrijftellers:
    // java.lang.Object-objecten, om wait en notifyAll te hebben
    @Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")
    private val canRead = Object()
    @Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")
    private val canWrite = Object()
    // de toegangsvoorwaarden van de tellers
    private var readingAllowed = false
    private var writingAllowed = false
    private var nextReader = 0
    private var nextWriter = 0
    // de volgorde van de lezers en van de schrijvers
    var readOrder = listOf<String>()
    var writeOrder = listOf<String>()

    // opent de schrijfteller
    fun allowWriting() {
        synchronized(canWrite) {
            writingAllowed = true
            // we maken alle schrijvers wakker die op het token wachten
            canWrite.notifyAll()
        }
    }

    // de inhoud van de array lezen
    fun read() {
        val name = Thread.currentThread().name
        println("Function [read] started by thread $name")
        // het token van de leesteller wordt aangevraagd
        synchronized(canRead) {
            try {
                // zolang het niet onze beurt is, geven we het token terug en wachten we
                while (!readingAllowed || readOrder[nextReader] != name) {
                    canRead.wait()
                }
            } catch (_: InterruptedException) {
                return
            }
            // bij de teller: de array lezen
            for (number in data) {
                sleep(500)
                println("${time()} : reader $name read the number $number")
            }
            // volgende lezer
            readingAllowed = false
            nextReader++
            // de schrijvers krijgen te horen dat ze mogen schrijven
            synchronized(canWrite) {
                writingAllowed = true
                canWrite.notifyAll()
            }
            println("Function [read] finished by thread $name")
        }
    }

    // naar de array schrijven
    fun write() {
        val name = Thread.currentThread().name
        println("Function [write] started by thread $name")
        // het token van de schrijfteller wordt aangevraagd
        synchronized(canWrite) {
            try {
                // zolang het niet onze beurt is, geven we het token terug en wachten we
                while (!writingAllowed || writeOrder[nextWriter] != name) {
                    canWrite.wait()
                }
            } catch (_: InterruptedException) {
                return
            }
            // bij de teller: de array schrijven
            for (i in data.indices) {
                sleep(500)
                data[i] = Random.nextInt(0, 1000)
                println("${time()} : writer $name wrote the number ${data[i]}")
            }
            // volgende schrijver
            writingAllowed = false
            nextWriter++
            // de lezers krijgen te horen dat ze mogen lezen
            synchronized(canRead) {
                readingAllowed = true
                canRead.notifyAll()
            }
            println("Function [write] finished by thread $name")
        }
    }
}

    8.8.4. Condities: de interface Condition

        lock.withLock {
            try {
                // zolang het niet onze beurt is, geven we de lock terug en wachten we op een signaal
                while (!writingAllowed || writeOrder[nextWriter] != name) {
                    canWrite.await()
                }
            } catch (_: InterruptedException) {
                Thread.currentThread().interrupt()
                return
            }
            // bij de teller: de array schrijven
            for (i in data.indices) {
                sleep(500)
                data[i] = Random.nextInt(0, 1000)
                println("${time()} : writer $name wrote the number ${data[i]}")
            }
            // volgende schrijver
            writingAllowed = false
            nextWriter++
            // de lezers krijgen te horen dat ze mogen lezen
            readingAllowed = true
            canRead.signalAll()
            println("Function [write] finished by thread $name")
        }
    }
}

    8.8.5. Meerdere gelijktijdige lezers: ReadWriteLock

    In de vorige voorbeelden waren lezers exclusief. In veel toepassingen is dat onnodig beperkend: meerdere threads kunnen tegelijk gegevens lezen terwijl niemand ze wijzigt. Alleen schrijven moet exclusief zijn: terwijl een schrijver de gegevens wijzigt, mag geen enkele lezer of andere schrijver er toegang toe hebben. Dit is het klassieke lezer-schrijver-probleem, dat wordt opgelost door de interface [java.util.concurrent.locks.ReadWriteLock]. Een object [ReadWriteLock] biedt twee gekoppelde locks:

    • [readLock()]: de leeslock, die door meerdere threads tegelijk kan worden vastgehouden, zolang geen enkele thread de schrijflock bezit;
    • [writeLock()]: de schrijflock, die exclusief is.

    De standaardbibliotheek van Kotlin voegt twee extensiefuncties uit het pakket [kotlin.concurrent] toe aan de klasse [ReentrantReadWriteLock] (die deze interface implementeert); ze zijn vergelijkbaar met [withLock]: [read { … }] voert het blok uit terwijl de leeslock wordt vastgehouden, en [write { … }] voert het blok uit terwijl de schrijflock wordt vastgehouden; beide geven de lock aan het einde van het blok vrij en geven de waarde van het blok terug.     private val prices = mutableMapOf("keyboard" to 20, "mouse" to 10)
    // één lock voor de lezers, één lock voor de schrijvers
    private val lock = ReentrantReadWriteLock()

    // meerdere threads kunnen tegelijk de leeslock bezitten
    fun readPrice(article: String): Int = lock.read {
        val name = Thread.currentThread().name
        println("${time()} : $name starts reading the price of $article")
        // lang lezen
        sleep(1000)
        val p = prices.getValue(article)
        println("${time()} : $name read the price of $article: $p")
        p
    }

    // de schrijflock is exclusief: geen lezer, geen andere schrijver
    fun changePrice(article: String, newPrice: Int) {
        val name = Thread.currentThread().name
        println("${time()} : $name requests the write lock")
        lock.write {
            println("${time()} : $name starts changing the price of $article")
            // lang schrijven
            sleep(1000)
            prices[article] = newPrice
            println("${time()} : $name set the price of $article to $newPrice")
        }
    }
}

    8.9. Concurrente collecties

    De vorige voorbeelden beschermden zeer eenvoudige gedeelde gegevens (een teller, een array, een kleine dictionary). Wanneer threads een collectie delen (lijst, dictionary, wachtrij), zou men elke toegang met een lock kunnen beschermen. Maar gewone wijzigbare collecties – die van Kotlin ([mutableListOf], [mutableMapOf], [ArrayDeque]) evenals die van Java ([ArrayList], [HashMap]) – zijn niet ontworpen om door meerdere threads tegelijk te worden gewijzigd: onbeschermd gebruik kan leiden tot verlies van elementen, onverwachte uitzonderingen ([ConcurrentModificationException]) of zelfs tot beschadiging van de interne structuur van de collectie. Hetzelfde geldt voor de „read-only” collecties van Kotlin ([List], [Map]): dit type verhindert dat de code die de collectie ontvangt haar wijzigt, maar garandeert niet dat niemand anders haar wijzigt. De methoden [Collections.synchronizedList(…)], [Collections.synchronizedMap(…)]… verpakken een gewone collectie in een object waarvan elke methode van het type [synchronized] is: dat is veilig, maar alle threads concurreren om één lock, en het doorlopen van de collectie moet nog steeds handmatig worden beschermd. Sinds Java 5 biedt het pakket [java.util.concurrent] collecties die zijn ontworpen om zonder expliciete lock tussen threads te worden gedeeld. De standaardbibliotheek van Kotlin heeft geen equivalent voor de JVM: we gebruiken rechtstreeks die van de JDK, die de interfaces [MutableList] en [MutableMap] implementeren… en dus op dezelfde manier worden gebruikt als de collecties van Kotlin ([+=], [[ ]], [for], [filter], [map]…):

package threads23

import java.util.concurrent.CopyOnWriteArrayList
import kotlin.concurrent.thread

fun main() {
    // het gedeelde woordenboek: cijfer -> aantal trekkingen
    val draws = ConcurrentHashMap<Int, Int>()
    // de gedeelde lijst met rapporten van de threads
    val reports = CopyOnWriteArrayList<String>()

    // 4 threads trekken elk 100.000 willekeurige cijfers
    val nbDraws = 100_000
    val threads = List(4) { i ->
        thread(name = "T$i") {
            repeat(nbDraws) {
                val digit = Random.nextInt(0, 10)
                // de sleutel toevoegen met de waarde 1 of de bestaande waarde atomair bijwerken
                draws.merge(digit, 1, Int::plus)

            val name = Thread.currentThread().name
            reports += "thread %s finished its %,d draws".format(name, nbDraws)
        }
    }

    // de rapporten, in volgorde van binnenkomst
    for (report in reports) {
        println(report)
    }
    // de resultaten van de trekkingen, in volgorde van de sleutels
    for ((digit, count) in draws.toSortedMap()) {
        println("digit %d : %,6d draws".format(digit, count))

    val total = draws.values.sum()
    println("total: %,d draws (expected: %,d)".format(total, threads.size * nbDraws))

    8.9.2. Producenten en consumenten: BlockingQueue

    Het lezer-schrijverprobleem is een variant van het klassieke producent-consument-probleem: threads produceren gegevens die andere threads consumeren. De interface [BlockingQueue<E>] lost dit op zonder expliciete synchronisatiehulpmiddelen:

    • [put(element)] plaatst een element in de wachtrij. Als de wachtrij een beperkte capaciteit heeft en vol is, wordt de producent geblokkeerd totdat er een plaats vrijkomt;
    • [take()] haalt het element aan de kop van de wachtrij weg. Als de wachtrij leeg is, wordt de consument geblokkeerd totdat er een element aankomt;
    • [offer(element, timeout, unit)] en [poll(timeout, unit)] doen hetzelfde, met een maximale wachttijd; [offer(element)] en [poll()], die geen time-out hebben, blokkeren nooit: zij geven [false] of [null] terug bij mislukking (in Kotlin geeft [poll] een platformtype terug, [Int!], dat moet worden behandeld als een [Int?]).

    De wachtrij weet niet dat de productie is beëindigd. Een klassieke techniek bestaat erin aan het einde van de productie een speciale waarde – in het Engels „poison pill” genoemd – in de wachtrij te plaatsen: de consument die haar ophaalt, weet dat hij moet stoppen. package threads24

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.BlockingQueue
import kotlin.concurrent.thread

// de waarde die het einde van de productie aangeeft ("poison pill")
const val END = -1

fun main() {
    // een wachtrij van maximaal 3 elementen
    val queue: BlockingQueue<Int> = ArrayBlockingQueue(3)
    val nbConsumers = 2

    // de producent plaatst 8 getallen en meldt dan dat hij klaar is
    val producer = thread(start = false, name = "P") {
        try {
            for (i in 1..8) {
                // blokkerend als de wachtrij vol is
                queue.put(i)
                println("${time()} : P put $i (waiting elements: ${queue.size})")
                Thread.sleep(100)
            }
            // één eindmarkering per consument
            repeat(nbConsumers) { queue.put(END) }
            println("${time()} : P has finished")
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }

    // twee consumenten nemen de getallen tot aan de eindmarkering
    val consumers = List(nbConsumers) { i ->
        thread(start = false, name = "C${i + 1}") {
            val name = Thread.currentThread().name
            try {
                while (true) {
                    // blokkerend als de wachtrij leeg is
                    val number = queue.take()
                    if (number == END) break
                    println("${time()} : $name took $number")
                    // verwerking van het getal
                    Thread.sleep(600)
                }
                println("${time()} : $name has finished")
            } catch (_: InterruptedException) {
                Thread.currentThread().interrupt()
            }
        }
    }

    // alle threads starten en erop wachten
    val all = listOf(producer) + consumers
    all.forEach { it.start() }

    8.10. Threadpools: ExecutorService

    8.10.1. Het principe

    Tot nu toe hebben we, om threads te beheren, ze aangemaakt en vervolgens gestart, hetzij via [start()] hetzij via de functie [thread]. Het aanmaken van een platformthread is een relatief dure bewerking: het systeem moet er met name een stack voor reserveren, en elke thread neemt geheugen in beslag zolang hij bestaat. In Hoofdstuk 10 zullen we zien dat er verbindingspools bestaan: geopende verbindingen worden in reserve gehouden en uitgeleend aan threads die erom vragen, aangezien het openen van een verbinding kostbaar is. Een vergelijkbaar systeem bestaat voor threads: de threadpool.

    De JDK stelt een threadpool voor via de interface [java.util.concurrent.ExecutorService] (een „executor”): er worden geen threads meer aangemaakt; in plaats daarvan worden taken aan de executor toegewezen, die ze door zijn threads laat uitvoeren. Een thread die een taak heeft voltooid, wordt niet vernietigd; hij neemt de volgende taak op zich. De klasse [ThreadPoolExecutor], de meest gebruikte implementatie, werkt als volgt:

    • hij heeft een vast aantal threads („core pool size”): zolang dit aantal niet is bereikt, leidt elke nieuwe taak tot het aanmaken van een nieuwe thread;
    • daarna worden taken in een wachtrij (een [BlockingQueue]) geplaatst waaruit de threads ze ophalen;
    • als de wachtrij vol is, maakt de pool extra threads aan, tot een maximum aantal („maximum pool size”). Deze extra threads worden vernietigd als zij langer dan een bepaalde tijd inactief blijven;
    • als het maximum is bereikt en de wachtrij vol is, wordt de taak geweigerd: standaard werpt de methode die haar heeft aangeboden de uitzondering [RejectedExecutionException] op.

    De threadpool biedt twee voordelen: hij bespaart de tijd die nodig is om threads aan te maken (een paar threads kunnen honderden verzoeken afhandelen), en door het aantal threads te beperken, voorkomt hij dat de applicatie wordt overspoeld door te veel verzoeken.

    Een executor wordt beëindigd met zijn methode [shutdown] (hij accepteert geen nieuwe taken meer en zijn threads stoppen zodra de reeds ingediende taken zijn voltooid), eventueel gevolgd door [awaitTermination] (die wacht tot de taken klaar zijn), of met [shutdownNow] (die de lopende taken onderbreekt). Vanaf Java 19 breidt [ExecutorService] de interface [AutoCloseable] uit: zijn methode [close] roept [shutdown] aan en wacht vervolgens tot alle taken zijn voltooid. In Kotlin kunt u een executor dus gebruiken binnen een [use { … }]-blok – de extensiefunctie van [AutoCloseable] die de instructie [try] met een Java-resource vervangt (Hoofdstuk 3) – Bij het verlaten van het blok zijn alle toegewezen taken voltooid. package threads25

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.RejectedExecutionException
import java.util.concurrent.ThreadPoolExecutor
import java.util.concurrent.TimeUnit

// de informatie die aan elke job wordt doorgegeven
data class Data(val number: Int, val start: LocalTime, val duration: Int)

fun main() {
    Thread.currentThread().name = "Main"
    // 3 permanente threads, maximaal 5 threads, een wachtrij van 2 jobs
    ThreadPoolExecutor(3, 5, 60, TimeUnit.SECONDS, ArrayBlockingQueue(2)).use { pool ->
        // 8 jobs van 3 s worden aan de pool overhandigd
        for (i in 0..<8) {
            val data = Data(i, LocalTime.now(), 3)
            try {
                pool.execute { sleep(data, pool) }
            } catch (_: RejectedExecutionException) {
                println("${time()} : job no. $i was rejected by the pool")
            }
        }
        println("${time()} : thread Main handed the jobs to the pool and waits for their end")
        // het einde van het use-blok sluit de pool: close() wacht op het einde van de ingediende jobs
    }
    println("${time()} : end of thread Main")
}

// de job die door een thread van de pool wordt uitgevoerd
fun sleep(data: Data, pool: ThreadPoolExecutor) {
    // toestand van de pool
    val name = Thread.currentThread().name
    println("${time()} : job no. ${data.number} starts in thread $name" +
            " (threads: ${pool.poolSize}, active: ${pool.activeCount}, queued: ${pool.queue.size})")
    // [duration] seconden slapen
    try {
        Thread.sleep(data.duration * 1000L)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
    val duration = Duration.between(data.start, LocalTime.now()).toMillis() / 1000.0
    println("%s : job no. %d ends: scheduled for %d s, it lasted %.2f s since it was requested"
            .format(time(), data.number, data.duration, duration))
}

package threads26

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.Callable
import java.util.concurrent.ExecutionException
import java.util.concurrent.Executors
import java.util.concurrent.Future

fun main() {
    println("Main thread: ${Thread.currentThread()}")

    // 1 - een pool van 2 threads, automatisch gesloten aan het einde van het use-blok
    Executors.newFixedThreadPool(2).use { pool ->
        // drie taken die elk een resultaat van het type Int teruggeven
        val futures: List<Future<Int>> = List(3) { number ->
            pool.submit<Int> {
                val name = Thread.currentThread().name
                println("${time()} : task $number runs in thread $name")
                // werk
                Thread.sleep(500L * (number + 1))
                // het resultaat van de taak
                number * 10
            }
        }
        // de resultaten: get() wacht op het einde van de taak
        futures.forEachIndexed { i, future ->
            try {
                println("task $i: result ${future.get()}, state ${future.state()}")
            } catch (e: ExecutionException) {
                println("task $i in error: ${e.cause}")
            }
        }

        // een taak die een exception genereert
        val failed = pool.submit<Int> { fail() }
        try {
            failed.get()
        } catch (e: ExecutionException) {
            // de exception van de taak wordt verpakt in een ExecutionException
            val cause = e.cause!!
            println("${e::class.simpleName} containing ${cause::class.simpleName} : ${cause.message}")
        }
        println("task in error: state ${failed.state()}")
    }

    // 2 - één virtuele thread per taak; invokeAll dient een collectie taken in en wacht op hun einde
    Executors.newVirtualThreadPerTaskExecutor().use { executor ->
        val jobs = List(3) { number ->
            Callable {
                Thread.sleep(300)
                "job $number executed by ${Thread.currentThread()}"
            }
        }
        for (future in executor.invokeAll(jobs)) {
            // de taak is voltooid: resultNow() geeft het resultaat terug zonder te wachten
            println(future.resultNow())
        }
    }
}

Het volgende hoofdstuk introduceert de klasse [CompletableFuture] van de JDK, die dit mogelijk maakt, en vooral de oplossing van Kotlin: coroutines, met [async] en [Deferred] (het equivalent van een [Future] waarvan het resultaat wordt afgewacht met [await] zonder een thread te blokkeren). Tot slot biedt Java 25, als preview, gestructureerde concurrency ([StructuredTaskScope]), die een groep subtaken behandelt als één werkeenheid (als er één mislukt, worden de andere geannuleerd). Zij wordt in deze cursus niet gebruikt: de coroutines van Kotlin zijn op ditzelfde principe gebaseerd, dat al lang een standaardfunctie van Kotlin is, en Hoofdstuk 9 gaat er uitgebreid op in.

    8.11.1. Parallelle streams

    Laten we terugkeren naar het voornaamste gebruik van threads: alle processors benutten voor een tijdrovende berekening. De standaardbibliotheek van Kotlin biedt geen parallelle bewerkingen op collecties: haar functies ([filter], [map], [count]…) en haar sequences zijn sequentieel. Standaard heeft de gedeelde pool evenveel threads als er processors zijn, min één: de aanroepende thread voert de telling uit.

    8.11.2. Verdeel en heers: ForkJoinPool en RecursiveTask

Een thread die niets meer te doen heeft, „steelt” taken uit de wachtrij van een andere thread („work stealing”): de belasting wordt zo automatisch verdeeld. De threads die de virtuele threads dragen, vormen ook een [ForkJoinPool]: dit is de pool die we hebben gezien in de tekstuele weergave van de virtuele threads ([ForkJoinPool-1-worker-1]). fun main() {
    val N = 5_000_000

    val (nb, duration) = measureTimedValue { ForkJoinPool.commonPool().invoke(CountPrimes(2, N)) }
    println("common pool       : %,d prime numbers in %d ms".format(nb, duration.inWholeMilliseconds))

    // een pool van 4 threads, gesloten aan het einde van het use-blok
    ForkJoinPool(4).use { pool ->
        CountPrimes.chunks.clear()
        val (nb4, duration4) = measureTimedValue { pool.invoke(CountPrimes(2, N)) }
        println("pool of 4 threads : %,d prime numbers in %d ms".format(nb4, duration4.inWholeMilliseconds))
        println("tasks stolen by one thread from another: ${pool.stealCount}")
    }
    // de verdeling van de brokken over de threads van de laatste pool
    for ((name, nbChunks) in CountPrimes.chunks.toSortedMap()) {
        println("  %-25s : %d chunks processed".format(name, nbChunks))

// een taak die de priemgetallen van het interval [start, end[ telt
class CountPrimes(private val start: Int, private val end: Int) : RecursiveTask<Int>() {
    companion object {
        // onder deze drempel wordt het brok rechtstreeks verwerkt
        const val THRESHOLD = 100_000
        // het aantal brokken dat door elke thread is verwerkt
        val chunks = ConcurrentHashMap<String, Int>()
    }

    override fun compute(): Int {
        // brok klein genoeg: het wordt sequentieel verwerkt
        if (end - start <= THRESHOLD) {
            chunks.merge(Thread.currentThread().name, 1, Int::plus)
            return (start..<end).count { isPrime(it) }
        }
        // anders wordt het in tweeën gesneden
        val middle = (start + end) ushr 1
        val left = CountPrimes(start, middle)
        val right = CountPrimes(middle, end)
        // de linkerhelft wordt aan de pool overhandigd (een andere thread kan hem "stelen")
        left.fork()
        // de rechterhelft wordt door de huidige thread verwerkt
        val nbRight = right.compute()
        // we wachten op het resultaat van de linkerhelft en combineren de twee resultaten
        return left.join() + nbRight
    }
}

    8.12. Thread-lokale gegevens

    8.12.1. Het principe

    Neem een applicatie met drie lagen:

    Stel dat de applicatie meerdere gebruikers heeft, zoals een webapplicatie. Elk gebruikersverzoek wordt door een thread afgehandeld. De levenscyclus van de thread is als volgt:

    • de thread wordt aangemaakt (virtuele thread) of aangevraagd bij een threadpool om aan het verzoek van een gebruiker te voldoen;
    • als dit verzoek gegevens vereist, voert de thread een functie uit in de laag [ui], die een functie aanroept in de laag [business], die op haar beurt een functie aanroept in de laag [dao];
    • de thread geeft het antwoord aan de gebruiker terug. Daarna eindigt hij of wordt hij teruggegeven aan de threadpool.

    Tijdens de tweede stap kan het nuttig zijn dat de thread over eigen gegevens beschikt, dat wil zeggen gegevens die niet met andere threads worden gedeeld. Deze gegevens kunnen bijvoorbeeld toebehoren aan de specifieke gebruiker die door de thread wordt bediend en worden gebruikt in de verschillende lagen [ui, business, dao] zonder dat ze als parameter aan elke functie worden doorgegeven.

    De JDK biedt hiervoor twee hulpmiddelen, die Kotlin ongewijzigd gebruikt:

    • de klasse [ThreadLocal<T>] (Java 1.2): een object waarvan de waarde – gelezen met [get()] en geschreven met [set(value)] – voor elke thread verschillend is. De constructor [ThreadLocal.withInitial(factory)] levert de beginwaarde voor elke thread; de methode [remove()] wist de waarde van de huidige thread. De afgeleide klasse [InheritableThreadLocal<T>] geeft de waarde van de aanmakende thread door aan de nieuw aangemaakte thread;
    • de klasse [ScopedValue<T>] (definitief in Java 25): een waarde die aan een thread is gebonden voor een beperkt bereik van de code en binnen dat bereik niet kan worden gewijzigd.

    @Volatile

    Context.shared = 100
    Context.perThread.set(100)
    Context.user.set("admin")
    Context.language.set("fr")

    val threads = List(3) { number ->

    8.12.3. De klasse ScopedValue

    Een [ScopedValue<T>]-waarde is gebonden aan een waarde voor de uitvoering van een stuk code, het zogeheten bereik:

    • [ScopedValue.newInstance()] maakt een gebonden waarde aan, doorgaans opgeslagen in een eigenschap op het hoogste niveau of in een eigenschap van een object, die alleen-lezen is ([val]);
    • [ScopedValue.where(sv, value).run(action)] voert de actie uit (een [Runnable]) door [sv] aan [value] te binden. Zolang de actie – en alle functies die zij aanroept – in de huidige thread wordt uitgevoerd, geeft [sv.get()] [value] terug. Wanneer de actie is afgelopen, verdwijnt de binding: er is niets op te ruimen;
    • [ScopedValue.where(sv, value).call(op)] doet hetzelfde met een bewerking die een resultaat retourneert;
    • binnen de scope kan de waarde niet worden gewijzigd; ze kan alleen aan een andere waarde worden gebonden voor een geneste scope;
    • [isBound()] geeft aan of de waarde in de huidige thread is gebonden (Kotlin behandelt dit als een eigenschap [isBound]); [orElse(other)] levert de gebonden waarde of, als die ontbreekt, [other]. Buiten elke scope [get()] werpt de [NoSuchElementException]-exception.

class Transaction {
    companion object {
        private val counter = AtomicInteger()
    }

    private val undos = ArrayDeque<() -> Unit>()
    val number = counter.incrementAndGet()

    // registreert de bewerking die een update ongedaan maakt
    fun log(undo: () -> Unit) {
        undos.addFirst(undo)
    }

    // commit de transactie: de updates blijven behouden
    fun commit() {
        undos.clear()
    }

    // rolt de transactie terug: de updates worden ongedaan gemaakt, van de laatste naar de eerste
    fun rollback() {
        while (true) {
            val undo = undos.removeFirstOrNull() ?: break
            undo()
        }
    }
}

class Business(private val dao: IDao) : IBusiness {
    // invoegen van een lijst met artikelen: alles of niets
    override fun insertArticlesInTransaction(articles: List<Article>) {
        val name = Thread.currentThread().name
        // start van de transactie, opgeslagen in de thread-lokale gegevens
        val transaction = Transaction()
        ThreadContext.transaction.set(transaction)
        try {
            for (article in articles) {
                // de laag [dao] vindt de transactie in de thread
                dao.insertArticle(article)
                // gesimuleerde verwerking, die andere threads de tijd geeft om in te grijpen
                sleep(200)
            }
            transaction.commit()
            println("[$name] [business] transaction ${transaction.number} committed")
        } catch (e: RuntimeException) {
            transaction.rollback()
            println("[$name] [business] transaction ${transaction.number} rolled back")
            // de exception wordt opnieuw naar de aanroeper gegenereerd
            throw e
        } finally {
            // de thread heeft geen lopende transactie meer
            ThreadContext.transaction.remove()
        }
    }

    // invoegen van een lijst met artikelen zonder transactie
    override fun insertArticlesOutOfTransaction(articles: List<Article>) {
        articles.forEach(dao::insertArticle)
    }

    override fun getAllArticles(): List<Article> = dao.getAllArticles()

    override fun deleteAllArticles() = dao.deleteAllArticles()
}

// voert een actie uit en toont de eventuele exception
fun execute(action: () -> Unit) {
    try {
        action()
    } catch (e: RuntimeException) {
        println("[${Thread.currentThread().name}] ${e::class.simpleName} : ${e.message}")
    }
}

// [ms] milliseconden slapen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

    8.12.5. Conclusie

    Het vorige voorbeeld liet de waarde van thread-lokale gegevens voor transactiebeheer zien. Het moet niet precies zo worden overgenomen, maar het beschrijft nauwkeurig hoe frameworks werken: het transactiebeheer van Spring ([@Transactional]-annotatie) plaatst de transactie en de databaseverbinding in [ThreadLocal], die de gegevenstoegangslagen raadplegen zonder dat hun code de transactie hoeft te manipuleren; Hibernate kan op soortgelijke wijze de werksessie aan de huidige thread koppelen. We komen op deze hulpmiddelen terug in hoofdstuk 11. In nieuwe code, met name met virtuele threads, is een *[ScopedValue]* de aanbevolen manier om dit soort contextinformatie door te geven; bij coroutines is deze rol weggelegd voor de coroutinecontext (hoofdstuk 9).

    Threadsynchronisatie is een uitdagend vakgebied. In dit hoofdstuk zijn de belangrijkste hulpmiddelen geïntroduceerd; voor meer informatie:

    • het boek van Brian Goetz e.a., [Java Concurrency in Practice] (Addison-Wesley), dat nog steeds het standaardwerk over dit onderwerp is, ook al dateert het van vóór de virtuele threads. De voorbeelden zijn in Java, maar alles wat het zegt, geldt ook voor Kotlin op de JVM;
    • het onderdeel „Concurrency” van de Java-tutorial van Oracle: Lesson: Concurrency – het is oud, maar nog steeds correct voor de basis;
    • de documentatie van het pakket [java.util.concurrent]: Package java.util.concurrent, waarvan het onderdeel „Memory Consistency Properties” de „happens-before”-relaties samenvat;
    • de documentatie van het pakket [kotlin.concurrent] in de standaardbibliotheek van Kotlin ([thread], [withLock], [read], [write], [getOrSet]…): kotlin.concurrent;
    • de Java Enhancement Proposals (JEP) waarmee virtuele threads en scoped values zijn geïntroduceerd: JEP 444: Virtual Threads en JEP 506: Scoped Values.

    In moderne code worden objecten ([Thread]) zelden rechtstreeks gemanipuleerd. In Java geven we de voorkeur aan executors ([ExecutorService]), parallelle streams voor berekeningen en virtuele threads voor taken waarbij gewacht moet worden. Kotlin beschikt over al deze hulpmiddelen, maar biedt ook een eigen oplossing, die in het volgende hoofdstuk wordt gepresenteerd: coroutines. Een coroutine is een taak die zichzelf kan opschorten (tijdens netwerktoegang, databasetoegang of bestandstoegang) zonder de thread te blokkeren die haar uitvoert, en vervolgens kan hervatten, mogelijk in een andere thread; gestructureerde concurrency zorgt ervoor dat geen enkele coroutine wordt vergeten en dat fouten en annuleringen correct worden doorgegeven. De concepten in dit hoofdstuk blijven niettemin essentieel: coroutines worden in threads uitgevoerd en de gegevens die ze delen, moeten met dezelfde hulpmiddelen worden beschermd (locks, atomaire klassen, concurrente collecties), of met hun equivalenten voor coroutines ([Mutex], [Channel]…).
