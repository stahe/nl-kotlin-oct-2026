    7. Functionele typen, lambda's en gebeurtenissen

    In veel programma's moeten we niet gegevens maar gedrag doorgeven aan een functie: het sorteercriterium, de filtervoorwaarde of de actie die moet worden uitgevoerd wanneer er iets gebeurt. Kotlin komt aan deze behoefte tegemoet door functies als waarden te behandelen, net als alle andere: een functie heeft een type, het functionele type, dat bijvoorbeeld wordt genoteerd als [(Int, Int) -> Int]. Zo'n functie kan in een variabele worden opgeslagen, als parameter worden doorgegeven, als resultaat van een andere functie worden teruggegeven en worden uitgevoerd wanneer men dat wil. Een functie die een functie als parameter neemt of teruggeeft, heet een hogere-ordefunctie.

    Java heeft, ter herinnering, geen functionele typen: het steunt op functionele interfaces, interfaces met één abstracte methode ([Runnable], [Comparator], [Function<T, R>]…), en pas sinds Java 8 (2014) kunnen die worden geïmplementeerd met lambda-expressies en methodeverwijzingen. Kotlin ondersteunt lambda's sinds zijn allereerste versie en kan ook met de functionele interfaces van Java werken, omdat het Java-bibliotheken rechtstreeks gebruikt. We hebben al uitgebreid lambda's gebruikt zonder erop in te gaan, bij de collectiebewerkingen uit hoofdstuk 5: in [persons.filter { it.age >= 18 }]geven we een lambda door aan de functie [filter]. Dit hoofdstuk legt uit wat er achter deze syntaxis schuilgaat. Het sluit af met gebeurtenissen, die Kotlin, net als Java, afhandelt met „listeners”: functies, meestal lambda's, die zich registreren bij een zender om op de hoogte te worden gehouden van wat daar gebeurt. Grafische gebruikersinterfaces (Swing, JavaFX, Compose) en webframeworks steunen allebei op dit mechanisme: een klik op een knop of de komst van een HTTP-aanvraag wordt gesignaleerd aan de geregistreerde listeners. Deze cursus behandelt geen grafische gebruikersinterfaces; alle voorbeelden zijn consoleprogramma's.

    De programma's in dit hoofdstuk zijn georganiseerd in het Gradle-project [07-lambdas], met één pakket per programma: [src/main/kotlin/lambdas01/Lambdas01.kt], [src/main/kotlin/lambdas02/Lambdas02.kt]… Ze worden uitgevoerd met [gradlew -q run -Pmain=lambdas01.Lambdas01Kt] of door op de groene driehoek in IntelliJ of IDEA te klikken. Het project vereist geen andere bibliotheken dan de standaardbibliotheek van Kotlin: functionele typen, lambda's en scopefuncties zitten erin, en de interfaces in het pakket [java.util.function] zijn dezelfde als die in de JDK.

    7.1. Functionele typen en voorgedefinieerde functionele interfaces

    7.1.1. Het begrip functioneel type

    Een functioneel type beschrijft een model (ook wel handtekening of vorm genoemd) van een functie: de typen van haar parameters tussen haakjes, gevolgd door een pijl en vervolgens het type van haar returnwaarde. Een variabele van een functioneel type kan naar elke functie van deze vorm verwijzen en die uitvoeren. Hier volgen enkele voorbeelden:

    • [() -> Unit]: een functie zonder parameters die geen bruikbaar resultaat teruggeeft ([Unit] vervult de rol van [void] in Java);
    • [() -> String]: een functie zonder parameters die een tekenreeks teruggeeft;
    • [(Int) -> Boolean]: een functie die een geheel getal neemt en een boolean teruggeeft, met andere woorden een predicaat;
    • [(Int, Int) -> Int]: een functie die twee gehele getallen neemt en een geheel getal teruggeeft;
    • [(String) -> (Int) -> Int]: een functie die een tekenreeks neemt en… een functie van het type [(Int) -> Int] teruggeeft (de pijl wordt van rechts naar links gelezen);
    • [(() -> Unit)?]: een functie die afwezig kan zijn; de haakjes zijn nodig omdat [() -> Unit?] anders een functie zou aanduiden die een [Unit?] teruggeeft. Hier zien we de veiligheidseigenschap ten aanzien van [null] uit hoofdstuk 3: zo'n functie wordt aangeroepen met [f?.invoke()];
    • [String.(Int) -> String]: een functie met een receiver; zij wordt toegepast op een tekenreeks, die haar code aanduidt als [this], als een extensiefunctie (hoofdstuk 4). Zij kan worden aangeroepen als extensie (["ab".f(3)]) of als gewone functie waarvan de receiver de eerste parameter is ([f("ab", 3)]).

    Parameters kunnen een naam krijgen om het type te documenteren: [(n1: Int, n2: Int) -> Int] is hetzelfde type als [(Int, Int) -> Int].

    Er zijn drie manieren om een waarde van een functioneel type te verkrijgen:

    • een verwijzing schrijven naar een bestaande functie die de juiste vorm heeft: [val task: () -> Unit = ::display];
    • een lambda-expressie schrijven: [val task: () -> Unit = { println("task") }];
    • een anonieme functie schrijven: [val task = fun() { println("task") }], of een object van een klasse die het functionele type implementeert (een functioneel type is een interface, zoals we zullen zien). Deze twee notaties komen minder vaak voor.

    De functie wordt vervolgens uitgevoerd als een gewone functie: [task()]. Dit is een verkorte notatie voor het aanroepen van de methode [invoke] van het functieobject: [task.invoke()]. Dit is het eerste merkbare verschil met Java, waar u de methode van de interface bij naam moet aanroepen ([run], [apply], [test]…); Kotlin gedraagt zich hier als C#, waar een delegate als een methode wordt aangeroepen.

    7.1.2. Functionele typen van Kotlin en interfaces uit java.util.function

Java 8 introduceerde het pakket [java.util.function], dat 43 generieke functionele interfaces biedt. Kotlin heeft ze niet nodig: een functioneel type wordt rechtstreeks geschreven. Deze interfaces kunnen echter nog steeds vanuit Kotlin worden gebruikt en u zult ze tegenkomen telkens wanneer u een Java-bibliotheek aanroept.     De Java-versies voor primitieve typen

    In Kotlin is er geen praktische limiet aan het aantal parameters dat een functioneel type kan hebben: [(Int, Int, Int) -> Int] is even eenvoudig te schrijven als de andere, terwijl u in Java, omdat er geen voorgedefinieerde interface met drie parameters bestaat, uw eigen interface moet definiëren.

    Hoe stelt de Java Virtual Machine, die alleen klassen en interfaces kent, een functioneel type voor? Via generieke interfaces uit de bibliotheek van Kotlin: [kotlin.jvm.functions.Function0<R>], [Function1<P1, R>], [Function2<P1, P2, R>]… tot en met [Function22], gevolgd door een interface [FunctionN] daarboven. Elk daarvan heeft één methode, [invoke]: [(Int, Int) -> Int] wordt gecompileerd tot [Function2<Integer, Integer, Integer>], waarvan de methode [operator fun invoke(p1: Int, p2: Int): Int] is. Het is de modifier [operator] van [invoke] (zie het overladen van operatoren in hoofdstuk 4) die de notatie [f(2, 3)] mogelijk maakt. Een functioneel type is voor de JVM dus een functionele interface zoals die van Java. Omdat Java-generics alleen op objecttypen van toepassing zijn, worden [Int]-waarden die aan een [(Int, Int) -> Int] worden doorgegeven, omgezet in [Integer] en omgekeerd (boxing en unboxing). Java vermijdt deze omzettingen met zijn gespecialiseerde interfaces ([IntBinaryOperator]…); Kotlin vermijdt ze op een andere manier, met de [inline]-functies, die we later bespreken.

    package lambdas01

import java.util.function.IntBinaryOperator
import java.util.function.Predicate
import java.util.function.Supplier

// Kotlin-functietypen en Java-functionele interfaces

fun main() {
    // 1 - () -> Unit: geen parameter, geen resultaat
    val task: () -> Unit = ::display
    // uitvoering: de functie wordt aangeroepen als een gewone functie
    task()
    // wat een afkorting is voor het aanroepen van de methode invoke
    task.invoke()

    // 2 - (Int, Int) -> Int: twee parameters, één resultaat
    val operation: (Int, Int) -> Int = ::add
    println("operation(2, 3)=${operation(2, 3)}")
    // () -> String: geen parameter, één resultaat
    val greet: () -> String = ::greet
    println("greet()=${greet()}")

    // 3 - (String) -> Unit: één parameter, geen resultaat
    val write: (String) -> Unit = ::println
    write("(String) -> Unit executed println")

    // 4 - (Int) -> Boolean: een predicaat
    val isEven: (Int) -> Boolean = ::isEven
    println("isEven(8)=${isEven(8)}")
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    // removeAll uit de Kotlin-bibliotheek verwacht een (Int) -> Boolean
    val modified = numbers.removeAll(isEven)
    println("even numbers removed: $modified, remaining: $numbers")

    // 5 - een Comparator<T> (Java-interface) opgebouwd uit een functie (SAM-conversie)
    val names = mutableListOf("Paul", "Mélanie", "Jo", "Sébastien")
    names.sortWith(Comparator(::compareLengths))
    println("sorted by length: $names")

    // 6 - de interfaces van java.util.function blijven bruikbaar
    val supplier: Supplier<String> = Supplier(::greet)
    val multiply = IntBinaryOperator(::multiply)
    val predicate = Predicate<Int> { it > 4 }
    println("supplier.get()=${supplier.get()}")
    println("multiply.applyAsInt(2, 3)=${multiply.applyAsInt(2, 3)}")
    // removeIf is een Java-methode (Collection): ze verwacht een Predicate
    val values = mutableListOf(10, 3, 8, 7, 2, 1)
    values.removeIf(predicate)
    // een Kotlin-functie wordt automatisch omgezet naar een Predicate (SAM-conversie)
    values.removeIf(isEven)
    values.removeIf { it == 1 }
    println("after removeIf: $values")

    // 7 - een nullable functietype: de functie kan ontbreken
    execute(null)
    execute(task)

    // 8 - een functietype met receiver: String.(Int) -> String
    val times: String.(Int) -> String = String::repeat
    println("\"ab\".times(3)=${"ab".times(3)}, times(\"cd\", 2)=${times("cd", 2)}")

    // 9 - een functie is een object, een instantie van een klasse die een interface implementeert
    println("class: ${operation::class.java.name}")
    println("interfaces: ${operation::class.java.interfaces.contentToString()}")
    val sum: (Int, Int) -> Int = { n1, n2 -> n1 + n2 }
    println("class of the lambda: ${sum::class.java.name}")
    println("interfaces: ${sum::class.java.interfaces.contentToString()}")
}

// een functie die een mogelijk ontbrekende functie ontvangt
fun execute(callback: (() -> Unit)?) {
    // safe call: er wordt niets uitgevoerd als callback null is
    callback?.invoke()
    println("callback ${if (callback == null) "absent" else "present"}")
}

// de functies waarnaar wordt verwezen: top-level functies van het bestand
fun display() {
    println("display() executed by task()")
}

fun multiply(n1: Int, n2: Int): Int = n1 * n2

fun greet(): String = "Hello"

fun isEven(n: Int): Boolean = n % 2 == 0

fun compareLengths(s1: String, s2: String): Int = s1.length.compareTo(s2.length)

    Opmerkingen:

    • regel 11: de variabele [task] is van het type [() -> Unit]. Eraan wordt een functieverwijzing toegekend: [::display] verwijst naar de top-levelfunctie [display] die verderop in het bestand is gedeclareerd (regel 79). De compiler controleert of zij de vereiste vorm heeft (geen parameters, geen returnwaarde) en maakt het functieobject dat haar aanroept. In Java zou een hulpklasse nodig zijn geweest om deze methoden te bevatten, omdat de impliciete klasse van een compact bronbestand geen naam kan krijgen; in Kotlin wordt rechtstreeks naar top-levelfuncties verwezen;
    • regel 13: de functie wordt uitgevoerd door haar als gewone functie aan te roepen. De functie [display] wordt uitgevoerd (regel 1 van de resultaten). Regel 15: hetzelfde resultaat wordt verkregen door de methode [invoke] expliciet aan te roepen (regel 2 van de resultaten);
    • Regel 18: [(Int, Int) -> Int] verwijst naar een functie met twee parameters, [Int], en die een [Int] teruggeeft. De functie [add] (regel 83) is geschikt. De functie wordt aangeroepen via [operation(2, 3)] (regel 19);
    • regel 21: een functie zonder parameters die een tekenreeks teruggeeft, het equivalent van [Supplier<String>] in Java. Merk op dat de lokale variabele [greet] dezelfde naam heeft als de functie [greet]: in [::greet] verwijst dit naar de functie en in [greet()] naar de lokale variabele, die de functie verbergt;
    • Regel 25: een functie met één parameter, [String], die niets teruggeeft, het equivalent van [Consumer<String>] in Java. De functie [println] uit de standaardbibliotheek is overladen ([println(Int)], [println(Any?)]…): het is het verwachte type, [(String) -> Unit], dat de compiler in staat stelt de juiste overload te kiezen;
    • Regel 29: een predicaat, gelijkwaardig aan [Predicate<Integer>]. Regel 33: de extensiefunctie [removeAll] uit de bibliotheek van Kotlin verwacht specifiek een parameter van het type [(T) -> Boolean]: zij verwijdert uit de veranderlijke lijst alle elementen waarvoor het predicaat [true] oplevert, en geeft [true] terug als zij ten minste één element heeft verwijderd (regel 7 van de resultaten);
    • Regel 38: de functie [sortWith] verwacht een [Comparator<T>]. In Kotlin is [Comparator] een alias voor de Java-interface [java.util.Comparator]. [Comparator(::compareLengths)] maakt een [Comparator<String>] van de functie [compareLengths]: dit is een SAM-conversie („Single Abstract Method”) die het object dat de Java-interface implementeert maakt van een Kotlin-functie van dezelfde vorm. De functie [compareLengths] (regel 91) gebruikt [compareTo], dat twee [Int]-objecten vergelijkt zonder het risico van overflow (dat een eenvoudige aftrekking niet uitsluit);
    • regels 42–44: de interfaces van *[java.util.function] kunnen als zodanig worden gebruikt. Ze worden op dezelfde manier geconstrueerd, via een expliciete SAM-conversie: de naam van de interface gevolgd door een functieverwijzing of een lambda. Ze worden vervolgens uitgevoerd via hun Java-methode ([get], [applyAsInt]*, [test]…), net als in Java;
    • regels 49–52: [removeIf] is een Java-methode van de interface [Collection]; zij verwacht een [Predicate]. U kunt haar een *[Predicate] doorgeven (regel 49), maar ook rechtstreeks een waarde van het type *[(Int) -> Boolean] (regel 51) of een lambda (regel 52): wanneer een Java-methode wordt aangeroepen die een functionele interface verwacht, voert Kotlin de SAM-conversie automatisch uit. Dat maakt Java-bibliotheken in Kotlin even prettig in het gebruik als in Java. De beginlijst (10, 3, 8, 7, 2, 1) verliest achtereenvolgens de elementen groter dan 4, de even elementen en dan het element 1 (regel 11 van de resultaten);
    • regels 56–57 en 72–75: aan de functie *[execute] wordt een functie doorgegeven die afwezig kan zijn, van het type *[(() -> Unit)?]. De veilige aanroep [callback?.invoke()] doet niets als [callback] gelijk is aan [null]. U kunt niet [callback?()] schrijven: de veilige aanroep van een nullable functie gaat via [invoke]. Dit wordt de standaardnotatie voor optionele listeners;
    • Regel 60: een functioneel type met een receiver. De verwijzing [String::repeat] verwijst naar de methode [repeat] van de klasse [String], die op een tekenreeks wordt toegepast en een geheel getal neemt. Regel 61 wordt op twee manieren aangeroepen: als extensie, ["ab".times(3)], of als functie met twee parameters, [times("cd", 2)]. Functies met een receiver komen we weer tegen bij de scopefuncties [apply] en [with];
    • regels 64–68: een functie is een object. De klasse van de functieverwijzing [operation] (regel 16 van de uitvoer) is een door de Kotlin-compiler gegenereerde klasse die is genoemd naar de plaats waar de verwijzing voorkomt; de klasse van de lambda [sum] (regel 18 van de resultaten) wordt tijdens de uitvoering door de virtuele machine gegenereerd, net als bij Java-lambda's: haar naam bevat [$$Lambda] gevolgd door een adres dat van uitvoering tot uitvoering verandert. In beide gevallen implementeert de klasse de interface [kotlin.jvm.functions.Function2] (regels 17 en 19 van de resultaten). Een Kotlin-functie is dus geen nieuw soort object: zij is een instantie van een gewone klasse die een functionele interface implementeert.

    7.2. Eigen functionele typen definiëren

    Functionele typen zijn vaak voldoende, maar u wilt soms een naam geven aan een functiemodel. Kotlin biedt hiervoor twee hulpmiddelen, die van zeer verschillende aard zijn.

    Het eerste is een typealias, gedeclareerd met het sleutelwoord [typealias]:

    • [typealias BinaryOperation = (n1: Int, n2: Int) -> Int]

    Een alias maakt geen nieuw type aan: [BinaryOperation] is een andere naam voor [(Int, Int) -> Int], en de twee notaties zijn uitwisselbaar. De alias maakt de code leesbaarder wanneer het functionele type lang is of vaak voorkomt.

    Het tweede is de functionele interface, gedeclareerd met [fun interface]:

    • [fun interface Operation { fun calculate(n1: Int, n2: Int): Int }]

    Dit is het exacte equivalent van een functionele Java-interface: een interface met slechts één abstracte methode (ook wel een SAM- of „Single Abstract Method”-interface genoemd). Zij kan ook methoden met een body en niet-abstracte eigenschappen hebben; die tellen niet mee. Het sleutelwoord [fun] vóór [interface] heeft dezelfde functie als de Java-annotatie [@FunctionalInterface], met één belangrijk verschil: het is niet optioneel. Dit sleutelwoord maakt de SAM-conversie mogelijk, dat wil zeggen het maken van een [Operation]-object uit een lambda of een functieverwijzing: [Operation { n1, n2 -> n1 + n2 }]. Zonder het sleutelwoord [fun] kan een Kotlin-interface, zelfs als zij tot één methode is beperkt, alleen worden geïmplementeerd door een klasse of een anoniem object ([object : Operation { … }]).

    In vergelijking met het type [(Int, Int) -> Int] is het type [Operation] een echt nieuw type, onderscheiden van alle andere: het heeft een naam die zijn doel beschrijft, zijn methode heeft een sprekende naam ([calculate] in plaats van [invoke]), het kan extra methoden hebben en het kan door een benoemde klasse worden geïmplementeerd. Omgekeerd wordt het uitgevoerd via de naam van zijn methode ([op.calculate(2, 3)]), niet met [op(2, 3)].

    Een variabele met de naam [op] van het type [Operation] verwijst, net als een variabele van het type [(Int, Int) -> Int], telkens naar slechts één functie tegelijk. In tegenstelling tot C#, dat „multicast delegates” kent, bieden Java noch Kotlin een manier om meerdere functies in één variabele op te slaan en ze met één aanroep allemaal uit te voeren: als dat nodig is, slaan we de functies op in een lijst en voeren we ze een voor een uit. Dat is precies wat we met listeners voor gebeurtenissen gaan doen.

    op = Operation(c1::add)
    n = op.calculate(2, 3)
    println("n=$n")
    // vervolgens de methode subtract van c1
    op = Operation(c1::subtract)
    n = op.calculate(2, 3)
    println("n=$n")

    // een variabele verwijst naar slechts één functie: om er meerdere uit te voeren, wordt een lijst gebruikt
    val operations = listOf(
        Operation(c1::add),
        Operation(c1::subtract),
        Operation { n1, n2 -> n1 * n2 },
    )
    for (operation in operations) {
        println("-> ${operation.calculate(10, 4)}")
    }

    // een methode van de interface bouwt een nieuwe bewerking
    val squaredSum = Operation(c1::add).then { x -> x * x }
    println("squaredSum.calculate(1, 2)=${squaredSum.calculate(1, 2)}")

    // Operation en IntBinaryOperator hebben dezelfde vorm maar zijn twee verschillende typen
    val other = IntBinaryOperator(op::calculate)
    println("other.applyAsInt(5, 1)=${other.applyAsInt(5, 1)}")

    // een generieke functionele interface
    val length = Transformation(String::length)
    val stars = Transformation("*"::repeat)
    println("length(\"Hello\")=${length.transform("Hello")}")
    println("stars(5)=${stars.transform(5)}")

    // een typealias: gewoon een andere naam voor (Int, Int) -> Int
    val f: BinaryOperation = { n1, n2 -> n1 - n2 }
    // BinaryOperation en (Int, Int) -> Int zijn hetzelfde type
    val g: (Int, Int) -> Int = f
    // maar Operation is een ander type: een conversie is nodig
    val op2 = Operation(g)
    println("f(5, 1)=${f(5, 1)}, g(5, 1)=${g(5, 1)}, op2.calculate(5, 1)=${op2.calculate(5, 1)}")
}

// definitie van een functionele interface: één abstracte methode
// die twee gehele getallen als parameters neemt en een geheel getal teruggeeft
fun interface Operation {
    fun calculate(n1: Int, n2: Int): Int

    // een methode met een body telt niet mee: de interface blijft functioneel
    fun then(next: (Int) -> Int): Operation = Operation { n1, n2 -> next(calculate(n1, n2)) }
}

// een generieke functionele interface: T -> R
fun interface Transformation<T, R> {
    fun transform(value: T): R
}

// een typealias: er wordt geen nieuw type aangemaakt
typealias BinaryOperation = (n1: Int, n2: Int) -> Int

// van anonieme objecten naar lambda-expressies

fun main() {
    // 1 - een anoniem object: de klasse die het functietype implementeert, wordt ter plekke geschreven
    val add = object : (Int, Int) -> Int {
        override fun invoke(n1: Int, n2: Int): Int {
            return n1 + n2
        }
    }
    println("anonymous object: add(2, 3)=${add(2, 3)}")

    // 2 - hetzelfde met een lambda-expressie: { parameters -> body }
    val subtract = { n1: Int, n2: Int -> n1 - n2 }
    println("lambda with typed parameters: subtract(2, 3)=${subtract(2, 3)}")

    // 3 - de parametertypen worden afgeleid uit het verwachte type
    val multiply: (Int, Int) -> Int = { n1, n2 -> n1 * n2 }
    println("lambda with untyped parameters: multiply(2, 3)=${multiply(2, 3)}")

    // 4 - één enkele parameter: die hoeft niet te worden benoemd en heet dan it
    val square: (Int) -> Int = { it * it }
    val isEmpty: (String) -> Boolean = { s -> s.isEmpty() }
    println("square(7)=${square(7)}, isEmpty(\"\")=${isEmpty("")}")

    // 5 - geen parameter: geen pijl
    val greet = { "Hello" }
    val beep = { println("beep!") }
    println(greet())
    beep()

    // 6 - een body met meerdere statements: de waarde van de laatste expressie is het resultaat
    val repeat: (String, Int) -> String = { text, times ->
        val buffer = StringBuilder()
        for (i in 1..times) {
            buffer.append(text)
        }
        buffer.toString()
    }
    println(repeat("ab", 3))

    // 7 - ongebruikte parameters: _
    val listener: (Any?, String) -> Unit = { _, _ -> println("event received") }
    listener(null, "click")

    // 8 - een lambda die als parameter wordt doorgegeven: buiten de haakjes als het de laatste parameter is
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    val evens = numbers.filter { it % 2 == 0 }
    println("evens: $evens")
    numbers.sortWith { n1, n2 -> n2.compareTo(n1) }
    println("descending order: $numbers")
    // de lambda buiten de haakjes, na andere parameters
    val total = numbers.fold(0) { acc, n -> acc + n }
    println("total: $total")

    // 9 - return in een lambda: return@label verlaat alleen de lambda
    numbers.forEach {
        if (it % 2 == 0) return@forEach
        print("$it ")
    }
    println("<- odds")
    // een label dat door de ontwikkelaar is gekozen
    numbers.forEach odd@{ n ->
        if (n % 2 != 0) return@odd
        print("$n ")
    }
    println("<- evens")
    // een anonieme functie: return verlaat daar de anonieme functie
    val isLarge = fun(n: Int): Boolean {
        if (n > 5) return true
        return false
    }
    println("large: ${numbers.filter(isLarge)}")

    // 10 - destructuring van de parameters van een lambda
    val ages = mapOf("Paul" to 40, "Mélanie" to 35)
    ages.forEach { (name, age) -> println("$name is $age years old") }
}

    • regels 7–12: een anoniem object. Het sleutelwoord [object] wordt gevolgd door een dubbele punt en het te implementeren type, in dit geval het functionele type [(Int, Int) -> Int] (dit is een interface, zoals we hebben gezien), en de body van een klasse die dit type implementeert door haar methode [invoke] te herdefiniëren. De compiler genereert een naamloze klasse en maakt er een instantie van. Zes regels om [n1 + n2] uit te drukken. Toch wordt het als een functie uitgevoerd: [add(2, 3)];
    • regel 15: hetzelfde met een lambda-expressie. Een lambda wordt geschreven tussen accolades: de lijst met parameters, de operator [->] (een pijl, die wordt gelezen als „geeft”) en vervolgens de body. De typenaam en de methodenaam zijn verdwenen. Omdat de parameters een type hebben, kan de compiler het type van de lambda zelf bepalen: [(Int, Int) -> Int]. Dit verschilt van Java, waar een lambda nooit een eigen type heeft;
    • regel 19: de typen van de parameters zijn weggelaten. De compiler leidt ze af uit het verwachte type dat voor de variabele is gedeclareerd: [n1] en [n2] zijn van het type [Int]. Dit is de meest gebruikelijke vorm. In Kotlin is er geen onderscheid tussen een „expressiebody” en een „blokbody” zoals in Java: de body van een lambda is een reeks statements en de waarde van de laatste expressie is het resultaat van de lambda;
    • Regel 23: bij één parameter hoeft u deze helemaal niet te declareren, en de pijl evenmin; ze heet dan impliciet [it] (Engels voor „het”). [{ it * it }] leest als „het kwadraat ervan”. Regel 24: de enige parameter heet [s]. Dit doet men wanneer [it] de code minder leesbaar zou maken, met name bij geneste lambda's (elke lambda zou zijn eigen [it] hebben);
    • Regels 28–29: zonder parameter is er geen pijl. Het type van *[greet]* wordt afgeleid als *[() -> String]*; het type van *[beep] is *[() -> Unit]*, aangezien *[println] als resultaat *[Unit]* heeft;
    • Regels 34–39: een lambda kan alle instructies bevatten: declaraties, lussen, tests enz. De waarde van de laatste expressie, [buffer.toString()], is het resultaat. U kunt niet [return buffer.toString()] schrijven: in een lambda verlaat een [return] zonder label de lambda niet (zie hieronder);
    • regel 44: het onderstrepingsteken [_] geeft een ongebruikte parameter aan. Het wordt gebruikt wanneer de typesignatuur parameters vereist die de lambda niet nodig heeft, wat bij listeners voor gebeurtenissen vaak voorkomt. U kunt meerdere van zulke parameters in dezelfde lambda opnemen (Java heeft deze syntaxis in versie 22 overgenomen);
    • Regels 48–49: het meest gebruikelijke gebruik van lambda's is ze rechtstreeks als parameters door te geven aan een hogere-ordefunctie. Wanneer de lambda de laatste parameter is, wordt zij buiten de haakjes geschreven; als er geen andere parameters zijn, worden de haakjes weggelaten: [numbers.filter { it % 2 == 0 }] in plaats van [numbers.filter({ it % 2 == 0 })]. Deze regel geeft Kotlin-code zijn kenmerkende uiterlijk en maakt het mogelijk functies te schrijven die op taalinstructies lijken ([repeat], [use], [thread], [synchronized]…). Vergelijk dit met [Lambdas01.kt]: het is niet langer nodig een functie [isEven] te schrijven;
    • regel 51: een lambda die de gebruikelijke vergelijking omkeert: de lijst wordt aflopend gesorteerd. [sortWith] verwacht een [Comparator] (een Java-interface): de SAM-conversie gebeurt automatisch;
    • regel 54: de lambda blijft buiten de haakjes wanneer de functie andere parameters heeft: [fold(0) { acc, n -> acc + n }]. De functie [fold] (hoofdstuk 5) begint met de beginwaarde 0 en telt de elementen een voor een op;
    • regels 58–62: binnen een lambda zorgt de instructie [return@forEach] ervoor dat de lambda wordt verlaten (en dus wordt doorgegaan met het volgende element), net als een [continue] in een lus. Het label [@forEach] is impliciet: het is de naam van de functie waaraan de lambda wordt doorgegeven. Een [return] zonder label zou de hele functie [main] verlaten: dit heet een niet-lokale return en is alleen toegestaan in een lambda die wordt doorgegeven aan een functie als [inline] of [forEach] (we zullen zien waarom);
    • regels 64–68: u kunt het label ook kiezen door het vóór de openingsaccolade te plaatsen: [odd@{ … }], dan [return@odd];
    • regels 70–74: een anonieme functie. Zij wordt geschreven als een gewone functie, maar zonder naam. Haar type wordt afgeleid: [(Int) -> Boolean]. In een anonieme functie verlaat [return] de anonieme functie zelf. Dit wordt gebruikt wanneer de body meerdere uitgangen heeft of wanneer u het type van het resultaat expliciet wilt opgeven;
    • Regel 78: de parameters van een lambda kunnen worden gedestructureerd (hoofdstuk 3). De lambda die aan [forEach] wordt doorgegeven, ontvangt een element van de associatieve array ([Map.Entry<String, Int>]); de notatie [(name, age)], tussen haakjes, ontleedt het in zijn sleutel en waarde. Let op: [{ name, age -> … }] zou twee parameters declareren, terwijl [{ (name, age) -> … }] zou één gedestructureerde parameter declareren.

import java.util.function.Function

// functies samenstellen: functies die functies teruggeven

fun main() {
    // 1 - samenstelling: onze extensies then (eerst this, dan de andere) en after (eerst de andere)
    val plusOne: (Int) -> Int = { it + 1 }
    val timesTwo: (Int) -> Int = { it * 2 }
    println("(plusOne then timesTwo)(5)=${(plusOne then timesTwo)(5)}")
    println("(plusOne after timesTwo)(5)=${(plusOne after timesTwo)(5)}")
    // de methoden van de Java-interface Function blijven beschikbaar
    val f = Function<Int, Int> { it + 1 }.andThen { it * 2 }
    println("Function.andThen: f.apply(5)=${f.apply(5)}")
    // een functie die functies maakt
    val plusTen = adder(10)
    println("adder(10)(5)=${plusTen(5)}, adder(3)(5)=${adder(3)(5)}")
    // een verwerkingsketen die uit een lijst met functies is opgebouwd
    val steps: List<(String) -> String> = listOf(String::trim, String::lowercase, { it.replace(' ', '-') })
    val normalize = steps.fold({ s: String -> s }) { function, step -> function then step }
    println("normalize(\"  My Nice Title \")=${normalize("  My Nice Title ")}")

    // 2 - predicaten: onze extensies and, or, not
    val short: (String) -> Boolean = { it.length <= 4 }
    val startsWithP: (String) -> Boolean = { it.startsWith("P") }
    val firstNames = listOf("Paul", "Mélanie", "Jo", "Sébastien", "Pierre")
    println("short and P: ${filterElements(firstNames, short and startsWithP)}")
    println("short or P: ${filterElements(firstNames, short or startsWithP)}")
    println("not short: ${filterElements(firstNames, !short)}")
    // een predicaat op CharSequence is geschikt voor het filteren van Strings
    val notEmpty: (CharSequence) -> Boolean = { it.isNotEmpty() }
    println("not empty: ${filterElements(listOf("a", "", "b"), notEmpty)}")

    // 3 - meerdere verwerkingen van dezelfde waarde
    val log = mutableListOf<String>()
    val display: (String) -> Unit = { println("display: $it") }
    val remember: (String) -> Unit = { log.add(it) }
    val both = display andAlso remember
    both("first")
    both("second")
    println("log: $log")

    // 4 - comparators: compareBy, thenBy, thenByDescending, reversed
    val persons = mutableListOf(Person("Paul", 32), Person("Mélanie", 25),
        Person("Jo", 32), Person("Sébastien", 25))
    persons.sortWith(compareBy(Person::age).thenBy(Person::name))
    println("by age then name: $persons")
    persons.sortWith(compareBy(Person::age).reversed().thenByDescending(Person::name))
    println("by descending age then descending name: $persons")
    // meerdere criteria tegelijk
    persons.sortWith(compareBy({ it.name.length }, { it.name }))
    println("by name length then name: $persons")
    // een comparator wordt ook gebruikt om de kleinste van twee elementen te kiezen
    val byAge = compareBy(Person::age)
    println("younger of Paul and Mélanie: ${minOf(persons[1], persons[2], byAge)}")
}

infix fun <T> ((T) -> Boolean).and(other: (T) -> Boolean): (T) -> Boolean = { this(it) && other(it) }

infix fun <T> ((T) -> Boolean).or(other: (T) -> Boolean): (T) -> Boolean = { this(it) || other(it) }

operator fun <T> ((T) -> Boolean).not(): (T) -> Boolean = { !this(it) }

// twee opeenvolgende verwerkingen van dezelfde waarde
infix fun <T> ((T) -> Unit).andAlso(other: (T) -> Unit): (T) -> Unit = { this(it); other(it) }

fun adder(n: Int): (Int) -> Int = { it + n }

// behoudt de elementen die aan het predicaat voldoen
fun <T> filterElements(elements: List<T>, predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in elements) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

    • regels 15–19: ditmaal legt de lambda een *[var]* vast, wat Java zou weigeren (*[local variables referenced from a lambda expression must be final or effectively final]). Zij ontvangt geen kopie van de waarde, maar deelt de variabele met de functie [main]: wanneer [variableThreshold] verandert in 10 (regel 19), geeft dezelfde lambda een ander resultaat (regels 2–3 van de resultaten). De lambdafunctie ziet dus de waarde van de variabele op het moment waarop zij wordt uitgevoerd*, niet op het moment waarop zij is gemaakt. Dit is het probleem dat Java vermijdt door deze captures te verbieden;
    • Regels 23–27: de lambda [accumulate] wijzigt de lokale variabele [total]. In Java moet u een veranderlijk object gebruiken ([AtomicInteger], of de omweg van een array met één element); in Kotlin schrijft u rechtstreeks [total += n];
    • regel 29: hoe is dit mogelijk, aangezien de virtuele machine zelf alleen toestaat dat waarden worden vastgelegd? De Kotlin-compiler doet het werk dat een Java-ontwikkelaar handmatig moet doen: een vastgelegde en gewijzigde lokale variabele [var] wordt niet meer op de stack opgeslagen, maar in een klein object van de klasse [kotlin.jvm.internal.Ref.IntRef] (er is er een voor elk primitief type, en *[Ref.ObjectRef] voor referenties), dat één veranderlijk veld heeft, *[element]. De functie [main] en de lambda delen dit object: elke lees- of schrijfbewerking op [total], in de een of de ander, wordt een lees- of schrijfbewerking op [total.element]. We kunnen dit via reflectie controleren: het enige veld van het lambdaobject is van het type [Ref$IntRef] (regel 5 van de resultaten). Dit is precies wat de C#-compiler met zijn vastgelegde variabelen doet;
    • regels 31–34: een lambda kan ook een top-levelvariabele (regel 6) of een eigenschap van het huidige object lezen en wijzigen. Hier is niets vast te leggen: de top-levelvariabele is een statisch veld van de klasse [Lambdas06Kt]; bij een eigenschap legt de lambda de verwijzing [this] vast;
    • regels 64–67: de functie [createCounter] geeft een lambda terug die haar lokale variabele [value] vastlegt en wijzigt. Normaal verdwijnt een lokale variabele wanneer de functie eindigt. Hier wordt de variabele opgeslagen in een object [Ref.IntRef] waarnaar de lambda verwijst: zij overleeft [createCounter] zolang de lambda bestaat. De combinatie van de lambda en de variabelen die zij vastlegt heet een „closure”;
    • regels 37–40: elke aanroep van *[createCounter] maakt een nieuwe variabele [value]*, en dus een nieuwe teller, onafhankelijk van de andere. De resultaten (regels 7–8) bevestigen dit;
    • regels 44–48: in een Kotlin-lus [for] is de variabele [i] een [val] die bij elke iteratie nieuw is: elke lambda legt haar eigen variabele vast en de drie lambda's tonen 0, 1 en 2. Merk op dat een lijst met functies wordt uitgevoerd via [actions.forEach { it() }]: [it] is een functie die wordt aangeroepen;
    • Regels 53–59: dit is de keerzijde van de flexibiliteit van Kotlin. De lus [while] gebruikt één enkele variabele, [k], die bij elke iteratie wordt gewijzigd. De drie lambda's leggen dezelfde variabele vast en tonen haar waarde wanneer zij worden uitgevoerd, dat wil zeggen na de lus, wanneer die gelijk is aan 3: ze tonen allemaal 3 (regel 10 van de resultaten). Java elimineert deze valkuil bij het compileren; in Kotlin is het aan de ontwikkelaar om dit af te handelen. De oplossing is dezelfde als in Java: declareer voor elke iteratie een nieuwe [val] in de body van de lus ([val copy = k]) en leg die vast, of gebruik, nog beter, een [for]-lus.

    De regel van Java heeft een gedegen rechtvaardiging: een lambda kan later of in een andere thread worden uitgevoerd (hoofdstuk 8). Als zij de lokale variabelen van een functie kan wijzigen, of ze kan lezen terwijl een andere thread ze wijzigt, kan dit tot onvoorspelbaar gedrag leiden. Kotlin kiest een andere, pragmatischer benadering: het vastleggen van [var] is toegestaan, maar de [Ref]-objecten zijn niet beschermd tegen gelijktijdige toegang. Laten we dus onthouden dat het vastleggen van een [var] veilig is in een single-threaded programma en in lambda's die onmiddellijk worden uitgevoerd ([forEach], [filter]…), maar dat zodra een lambda in een andere thread kan worden uitgevoerd, de gedeelde veranderlijke toestand expliciet moet worden gemaakt met een object waarvan het threadgedrag uitdrukkelijk is gekozen ([AtomicInteger], thread-safe collecties…). We komen hierop terug in de hoofdstukken 8 en 9. De [inline]-functies, die verderop worden gepresenteerd, voorkomen ook het maken van [Ref]-objecten wanneer de lambda in de aanroepende code wordt gekopieerd.

    7.4. Inline-functies en scopefuncties

    7.4.1. Inline-functies

    Een lambda is een object. Een lambda doorgeven aan een hogere-ordefunctie brengt dus kosten met zich mee: het maken van het object (behalve voor een lambda die niets vastlegt, die de virtuele machine kan hergebruiken), de aanroep van haar methode [invoke] , de omzettingen [Int] ↔ [Integer] die de generieke interfaces [Function1], [Function2]… opleggen, en de [Ref]-objecten van de vastgelegde variabelen. Voor een functie als [filter], die op elk element van soms zeer grote collecties wordt aangeroepen, zijn deze kosten van belang. Kotlin neemt ze weg met de modifier [inline]: wanneer een functie als [inline fun] is gedeclareerd, genereert de compiler geen aanroep van die functie; in plaats daarvan kopieert hij haar code naar elke plaats waar zij wordt aangeroepen, en kopieert hij ook de code van de lambda's die eraan zijn doorgegeven. Hierdoor zijn er geen lambdaobjecten meer, geen aanroepen van [invoke] en geen omzettingen. De functies van de standaardbibliotheek die lambda's accepteren ([forEach], [filter], [map], [fold], [let], [apply], [repeat], [use], [synchronized]…) zijn bijna allemaal [inline]. Java heeft geen equivalent: het vertrouwt op de just-in-timecompiler van de virtuele machine om een vergelijkbaar resultaat te behalen tijdens de uitvoering.

    De invoeging van de code heeft een tweede, opvallender gevolg: aangezien de code van de lambda in de aanroepende functie wordt gekopieerd, kan een [return]-instructie zonder label vanaf die plek de aanroepende functie verlaten. Dit is de niet-lokale return die we bij *[forEach] in *[Lambdas03.kt] zijn tegengekomen. Twee modifiers vullen *[inline]* aan:

    • [noinline], toegepast op een functieparameter van een [inline]-functie, geeft aan dat de bijbehorende lambda niet moet worden gekopieerd maar als gewoon object moet worden doorgegeven. Dit is nodig wanneer de functie de lambda wil bewaren (in een lijst opslaan, als resultaat teruggeven enz.): gekopieerde code kan niet in een lijst worden opgeslagen;
    • [crossinline] eist dat de lambda wordt gekopieerd, maar verbiedt niet-lokale returns. Dit is nodig wanneer de functie [inline] de lambda niet zelf uitvoert, maar in een andere context, bijvoorbeeld binnen een [Runnable]-object dat zij maakt: wanneer [Runnable] wordt uitgevoerd, kan de aanroepende functie al lang klaar zijn en zou een [return] haar niet meer kunnen verlaten.

// inline-, noinline- en crossinline-functies

fun main() {
    // 1 - een gewone functie ontvangt een functieobject; een inline-functie ontvangt de code van de lambda
    execute { println("lambda passed to execute, executed by: ${currentMethod()}") }
    executeInline { println("lambda passed to executeInline, executed by: ${currentMethod()}") }

    // 2 - de non-local return is alleen toegestaan in een lambda die aan een inline-functie wordt doorgegeven
    val numbers = listOf(3, 8, 1, 6)
    println("first even of $numbers: ${firstEven(numbers)}")

    // 3 - noinline: een lambda die als object moet worden bewaard
    val callbacks = mutableListOf<() -> Unit>()
    executeThenStore(callbacks, { println("executed right away") }, { println("stored callback") })
    println("${callbacks.size} stored callback, which we execute:")
    callbacks.forEach { it() }

    // 4 - crossinline: een lambda die in een andere context wordt uitgevoerd
    val task = asTask { println("executed by ${Thread.currentThread().name}") }
    val thread = Thread(task, "worker")
    thread.start()
    thread.join()
}

// de naam van de methode die currentMethod aanroept (gelezen uit de call stack)
fun currentMethod(): String = Throwable().stackTrace[1].methodName

// een gewone functie: block is een object van het type () -> Unit
fun execute(block: () -> Unit) {
    block()
}

// een inline-functie: de code ervan, en die van de lambda, wordt gekopieerd naar de plek waar ze wordt aangeroepen
inline fun executeInline(block: () -> Unit) {
    block()
}

// onze eigen forEach, inline zoals die van de bibliotheek
inline fun <T> forEachElement(elements: List<T>, action: (T) -> Unit) {
    for (element in elements) action(element)
}

fun firstEven(numbers: List<Int>): Int? {
    forEachElement(numbers) {
        // non-local return: we verlaten firstEven, en niet alleen de lambda
        if (it % 2 == 0) return it
    }
    return null
}

// immediate wordt gekopieerd; stored blijft een functieobject, dat in de lijst kan worden gezet
inline fun executeThenStore(
    callbacks: MutableList<() -> Unit>,
    immediate: () -> Unit,
    noinline stored: () -> Unit,
) {
    immediate()
    callbacks.add(stored)
}

// action wordt uitgevoerd in een Runnable-object, niet in asTask: een non-local return is daar onmogelijk
inline fun asTask(crossinline action: () -> Unit): Runnable = Runnable { action() }

    7.4.2. Scopefuncties

    • en dat is wat de functie retourneert: het resultaat van de lambda of het object zelf.

// de scope-functies: let, run, with, apply, also (en takeIf)

fun main() {
    // 1 - apply: configureert het object (this) en geeft het object terug
    val paul = Person("Paul").apply {
        age = 32
        city = "Angers"
    }
    println("apply: $paul")

    // 2 - also: een extra verwerking van het object (it), dat wordt teruggegeven
    val persons = mutableListOf<Person>()
    val melanie = Person("Mélanie", 25).also { persons.add(it) }
    println("also: $melanie, persons=$persons")

    // 3 - let: zet het object (it) om in een resultaat; veel gebruikt met ?.
    val length = paul.name.let { it.length * 2 }
    println("let: length=$length")
    for (city in listOf("Tours", null)) {
        val message = city?.let { "lives in ${it.uppercase()}" } ?: "unknown city"
        println("let and ?.: $message")
    }

    // 4 - run: een berekening op het object (this), die een resultaat teruggeeft
    val description = paul.run { "$name, $age years old, lives in $city" }
    println("run: $description")

    // 5 - with: zoals run, maar het object wordt als parameter doorgegeven
    val summary = with(StringBuilder()) {
        append("Persons: ")
        append(persons.joinToString { it.name })
        toString()
    }
    println("with: $summary")

    // 6 - takeIf: het object als het aan het predicaat voldoet, anders null
    for (age in listOf(15, 40)) {
        val adult = Person("Jo", age).takeIf { it.age >= 18 }
        println("takeIf: ${adult ?: "minor"}")
    }
}

class Person(val name: String, var age: Int = 0) {
    var city: String? = null

    override fun toString() = "Person(name=$name, age=$age, city=$city)"
}

    // een interface met twee abstracte methoden accepteert geen lambda meer: een klasse is nodig
    val division = object : NamedOperation {
        override fun calculate(n1: Int, n2: Int) = n1 / n2

        override val name = "integer division"
    }
    println("${division.name}: ${division.calculate(7, 2)}")
    // een klasse kan ook een functietype implementeren
    val modulo = Modulo()
    println("modulo(7, 2)=${modulo(7, 2)}, applyFunction(modulo)=${applyFunction(modulo, 7, 3)}")
}

    • regels 57–58: het omgekeerde geldt ook: een klasse kan een functietype implementeren, omdat dat een interface is. De instanties ervan worden dan aangeroepen als functies ([modulo(7, 2)]) en doorgegeven overal waar een functie wordt verwacht ([applyFunction(modulo, 7, 3)], regel 21).

    Deze twee voorbeelden laten zien dat in Kotlin, net als in Java, een functie die een gedrag verwacht objecten accepteert van klassen die daarvoor zijn geschreven, referenties en lambda's. Er blijven twee vragen over. De eerste is specifiek voor Kotlin: is voor een functionele parameter een functietype vereist, of volstaat een [fun interface]?

    • Het functietype is de standaardkeuze. Het vereist geen declaratie, wordt aangeroepen als een functie, accepteert rechtstreeks lambda's en referenties, en profiteert van [inline]-functies. Een [typealias] geeft het een naam wanneer het type lang is;
    • de „fun"-interface is gerechtvaardigd wanneer u een werkelijk apart type wilt (dat niet kan worden verward met een andere functie van dezelfde vorm), een methode met een beschrijvende naam, extra methoden met een body, of een API die ook bedoeld is voor Java-aanroepers: voor Java is een [fun interface] een gewone functionele interface, bruikbaar met lambda's, terwijl een Kotlin-functietype zich aan Java voordoet als een [Function2<Integer, Integer, Integer>] waarvan de methode [invoke] een object moet retourneren ([Unit] voor een functie zonder retourwaarde).

    De tweede vraag is dezelfde als in Java: moet de interface één methode hebben, of meerdere?

    • Een functie, functietype of interface met één methode is flexibeler in het gebruik: elke bestaande functie met de juiste vorm volstaat, en met een lambda kunt u de functie zelfs schrijven op de plek waar ze wordt aangeroepen. Er hoeft geen klasse te worden geschreven. Deze flexibiliteit verklaart waarom moderne bibliotheken (collecties, de coroutines in hoofdstuk 9, Spring) uitgebreid gebruikmaken van functionele parameters;
    • een interface met meerdere leden heeft weer het voordeel zodra het te implementeren gedrag meerdere samenhangende bewerkingen omvat ([calculate] en [name] hierboven), of wanneer het een eigen toestand en identiteit vereist.

    Dit is het geval voor de interface [ITaxDao] in de laag [dao] uit hoofdstuk 6: hoewel de interface slechts één lid heeft, namelijk de eigenschap [val taxBrackets: List<TaxBracket>], hebben de implementaties ervan een toestand (de ingelezen schijven, de bestandsnaam), worden ze aangemaakt door de dependency-injectiecontainer en vertegenwoordigen ze een duidelijk benoemde rol binnen de applicatie. Een [() -> List<TaxBracket>] zou technisch gezien hebben volstaan, maar zou veel minder beschrijvend zijn geweest. We reserveren functietypen dan ook voor korte, eenmalige gedragingen (een criterium, een transformatie, een actie), en „zakelijke" interfaces voor de rollen van de applicatie, ongeacht het aantal leden.

    7.6. Gebeurtenissen afhandelen

    7.6.1. Het observerpatroon

    Functies die als parameter worden doorgegeven, worden gebruikt om gebeurtenissen in te richten. Net als Java kent Kotlin geen specifiek sleutelwoord voor gebeurtenissen (C# heeft een eigen sleutelwoord, [event]): het volgt de conventies die Java al vanaf versie 1.1 hanteert voor grafische componenten en JavaBeans, bekend als het „listenermodel". Een klasse [C1] die een gebeurtenis [Xxx] wil melden, gaat als volgt te werk:

    • Een klasse [XxxEvent] kapselt informatie over de gebeurtenis in, waaronder het object dat de gebeurtenis heeft veroorzaakt, de zogeheten bron. In Java is het de conventie dat ze is afgeleid van [java.util.EventObject], die de bron opslaat; in Kotlin volstaat een gewone klasse met alleen-lezeneigenschappen, en dat is wat we doen;
    • Een listenertype definieert de vorm van de functie die wordt aangeroepen wanneer de gebeurtenis zich voordoet. In Java is dit een interface met de naam [XxxListener]; in Kotlin is het meestal een eenvoudig functietype, [(XxxEvent) -> Unit], een naam gegeven met een [typealias]: een listener is een lambda of een functiereferentie;
    • de klasse [C1] beheert een lijst met functies en biedt twee publieke methoden om zich daarvoor aan te melden en af te melden: [addXxxListener(listener)] en [removeXxxListener(listener)];
    • Wanneer een instantie [c1] van [C1] de gebeurtenis wil melden, maakt ze een object [XxxEvent] aan en roept ze elk van de geregistreerde listeners aan, waarbij ze dit object aan hen doorgeeft. Volgens afspraak wordt deze melding afgehandeld door een beveiligde methode [fireXxx(e: XxxEvent)] („fire"), die een afgeleide klasse kan overschrijven om te wijzigen hoe de gebeurtenis wordt gepubliceerd;
    • Als een object [c2] op de hoogte wil worden gesteld van de gebeurtenis [Xxx] van het object [c1], meldt het zich aan met [c1.addXxxListener(...)]. Het kan zich afmelden via [c1.removeXxxListener(...)] wanneer het geen meldingen meer wenst te ontvangen. Omdat [c1] een lijst beheert, kunnen verschillende objecten zich aanmelden om op de hoogte te worden gesteld van dezelfde gebeurtenis.

    In dit scenario hebben we:

    • een klasse die een gebeurtenis meldt (ook wel „publiceert" of „uitzendt");
    • objecten die van deze gebeurtenis op de hoogte worden gesteld. Ze zouden zich op de gebeurtenis abonneren of zich ervoor registreren: dit zijn de listeners, of gebeurtenishandlers;
    • een listenertype dat de vorm definieert van de functies die van de gebeurtenis op de hoogte worden gesteld.

    Dit is het ontwerppatroon Observer: de zender kent zijn abonnees niet; hij stelt hen alleen op de hoogte. Dit model biedt dezelfde bescherming als een speciaal sleutelwoord: de lijst met listeners is een privé-eigenschap van de zender. Van buitenaf kan men zich alleen aan- of afmelden; men kan de lijst niet leegmaken, andere listeners niet vervangen en de gebeurtenis niet in de plaats van de zender activeren.

// de klasse die de gebeurtenis meldt
open class Emitter(val name: String) {
    companion object {
        // drempel die de gebeurtenis activeert
        const val THRESHOLD = 19.0
    }

    // de geregistreerde listeners: een lijst met functies
    private val listeners = CopyOnWriteArrayList<TemperatureTooHighListener>()

    // waargenomen temperatuur: het schrijven van de property kan de gebeurtenis activeren
    var temperature = 0.0
        set(value) {
            field = value
            if (value > THRESHOLD) {
                // de gebeurtenis wordt aan de listeners gemeld
                fireTemperatureTooHigh(TemperatureTooHighEvent(this, value))
            }
        }

    // registratie van een listener
    fun addTemperatureTooHighListener(listener: TemperatureTooHighListener) {
        listeners.add(listener)
    }

    // deregistratie van een listener
    fun removeTemperatureTooHighListener(listener: TemperatureTooHighListener) {
        listeners.remove(listener)
    }

    // melding van de gebeurtenis aan alle geregistreerde listeners
    protected open fun fireTemperatureTooHigh(e: TemperatureTooHighEvent) {
        for (listener in listeners) {
            listener(e)
        }
    }
}

    • Regels 7–14: de klasse [TemperatureTooHighEvent] slaat de bron van de gebeurtenis op, van het type [Emitter], en de temperatuur die de gebeurtenis heeft veroorzaakt. We hebben het tijdstip van de gebeurtenis toegevoegd, [time], dat wordt geïnitialiseerd wanneer het object wordt aangemaakt.     • Regel 18: het type van de listener. Een listener is een functie die het gebeurtenisobject als argument neemt en niets retourneert. Waar Java een interface *[TemperatureTooHighListener]* vereist die is afgeleid van *[EventListener]*, gebruikt Kotlin eenvoudigweg een alias voor een functietype. We hadden evengoed een ***[fun interface TemperatureTooHighListener]*** kunnen declareren: dat zou de juiste keuze zijn als de listeners in Java zouden worden geschreven;
    • regel 24: de temperatuurdrempel waarboven de gebeurtenis [TemperatureTooHigh] wordt geactiveerd, een constante van het companion-object;
    • regel 21: de zender heeft een naam ter identificatie. De klasse is gedeclareerd als [open], zodat een afgeleide klasse de methode [fireTemperatureTooHigh] opnieuw kan definiëren;
    • regel 28: de lijst met geregistreerde listeners, een lijst met functies. Het is een [CopyOnWriteArrayList] uit het pakket [java.util.concurrent], een lijst die bij elke wijziging de inhoud naar een nieuwe array kopieert. Een lopende iteratie gaat daarom door op de oude array, ook als de lijst intussen wordt gewijzigd. We zullen later zien waarom dit hier essentieel is. Deze lijst is het standaardtype voor listenerlijsten: de lijst wordt voor elke gebeurtenis doorlopen, maar wordt zelden gewijzigd;

// een klasse die zich als listener van de gebeurtenis registreert
class Subscriber(
    // naam van de abonnee
    private val name: String,
    // maximaal aantal geaccepteerde alarmen
    private val nbMaxAlerts: Int,
) {
    // aantal ontvangen alarmen
    private var nbAlerts = 0

    // registratie bij een zender
    fun subscribe(emitter: Emitter) {
        emitter.addTemperatureTooHighListener(::onTemperatureTooHigh)
    }

    // deregistratie: een nieuwe referentie naar dezelfde methode van hetzelfde object is er gelijk aan
    fun unsubscribe(emitter: Emitter) {
        emitter.removeTemperatureTooHighListener(::onTemperatureTooHigh)
    }

    // handler van de gebeurtenis TemperatureTooHigh
    private fun onTemperatureTooHigh(e: TemperatureTooHighEvent) {
        val emitter = e.source
        val temperature = "%.1f".format(e.temperature)
        println("Subscriber [$name]: the source [${emitter.name}] " +
            "signaled a temperature that is too high: [$temperature]")
        // na nbMaxAlerts alarmen meldt de abonnee zich af
        nbAlerts++
        if (nbAlerts == nbMaxAlerts) {
            unsubscribe(emitter)
            println("Subscriber [$name]: unsubscribed after $nbAlerts alert(s)")
        }
    }
}

In Java zou dit een klassieke fout zijn: twee evaluaties van [this::onTemperatureTooHigh] leveren twee objecten op die [equals]* als verschillend beschouwt, en de afmelding zou niets verwijderen, zonder enige foutmelding; de listener moet slechts één keer worden aangemaakt en in een veld worden opgeslagen. Dat zou niet het geval zijn met een lambda: [{ e -> onTemperatureTooHigh(e) }]*, twee keer geschreven, zou twee verschillende objecten opleveren;

    7.6.3. Gebeurtenissen bij eigenschapswijzigingen

    Het meest voorkomende type gebeurtenis doet zich voor wanneer de waarde van een eigenschap van een object verandert: een ander object (een grafische gebruikersinterface, een cache, een logboek) wil van deze wijziging op de hoogte worden gesteld. Kotlin en de Java-bibliotheek bieden hiervoor twee complementaire hulpmiddelen:

    • de gedelegeerde eigenschappen van Kotlin. Een eigenschap die is gedeclareerd als [var p: T by delegate] delegeert het lezen en schrijven van haar waarde aan een ander object, de delegate. De standaardbibliotheek biedt er verschillende, zoals [by lazy { … }], die de waarde van de eigenschap bij de eerste toegang berekent. Het object [kotlin.properties.Delegates] biedt twee delegates die een lambda accepteren: [Delegates.observable(initialValue) { property, old, new -> … }] voert de lambda uit na elke schrijfbewerking op de eigenschap; [Delegates.vetoable(initialValue) { property, old, new -> … }] voert haar vooraf uit en accepteert de nieuwe waarde alleen als de lambda [true] retourneert. De parameter [property] is een referentie naar de eigenschap ([KProperty]), waarvan de naam wordt verkregen via [property.name];
    • de Java-klasse [java.beans.PropertyChangeSupport], die de lijst met listeners voor ons beheert. De listeners implementeren de functionele interface [PropertyChangeListener], waarvan de methode [void propertyChange(PropertyChangeEvent evt)] een gebeurtenis ontvangt met de bron, de naam van de eigenschap en haar oude en nieuwe waarde.

// een klasse waarvan de properties hun wijzigingen melden
class Thermometer(name: String) {
    // het beheer van de listeners wordt gedelegeerd aan een PropertyChangeSupport-object
    private val changes = PropertyChangeSupport(this)

    // een observeerbare property: na elke schrijfactie wordt de wijziging gemeld
    private fun <T> observable(initialValue: T): ReadWriteProperty<Any?, T> =
        Delegates.observable(initialValue) { property, old, new ->
            changes.firePropertyChange(property.name, old, new)
        }

    var name: String by observable(name)
    var temperature: Double by observable(0.0)

    // een property die waarden buiten het interval [5, 30] weigert
    var setpoint: Double by Delegates.vetoable(20.0) { _, _, new -> new in 5.0..30.0 }

    // registratie en deregistratie van de listeners
    fun addPropertyChangeListener(listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(listener)
    }

    fun addPropertyChangeListener(property: String, listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(property, listener)
    }

    fun removePropertyChangeListener(listener: PropertyChangeListener) {
        changes.removePropertyChangeListener(listener)
    }

    val nbListeners: Int
        get() = changes.propertyChangeListeners.size
}

fun main() {
    val numbers = listOf(3, 8, 1, 6, 5, 4, 9, 2)

    // 1 - filter en map verwachten functies (T) -> Boolean en (T) -> R
    val isEven: (Int) -> Boolean = { it % 2 == 0 }

    println("collections: ${numbers.filter(isEven).map(square)}")
    // de Java Stream API blijft bruikbaar: de lambda's worden omgezet naar Predicate en Function
    println("Stream: ${numbers.stream().filter { it % 2 == 0 }.map { it * it }.toList()}")

    // 2 - onze eigen filterfunctie, aangeroepen met een lambda en vervolgens met een referentie
    println("filterBy(n > 4): ${numbers.filterBy { it > 4 }}")
    println("filterBy(isOdd): ${numbers.filterBy(::isOdd)}")

    // 3 - een collectie wordt onmiddellijk geëvalueerd: elke stap levert een volledige lijst op
    val largeList = numbers.filter {
        print("[test $it] ")
        it > 7
    }
    println()
    println("the list is already computed: $largeList")

    // 4 - een sequence wordt op verzoek geëvalueerd:
    //     het predicaat wordt alleen door de terminale bewerking aangeroepen
    val large = numbers.asSequence().filter {
        print("[test $it] ")
        it > 7
    }
    println("the sequence is defined, nothing has been executed yet")
    large.forEach { print("-> $it ") }
    println()

    // 5 - onze eigen tussenbewerkingen op sequences, ook lazy
    val cities = listOf("Angers", "Paris", "Lyon", "Nantes", "Aix")
    val result = cities.asSequence()
        .keep { it.length <= 5 }
        .transform(String::uppercase)
        .toList()
    println("our operations: $result")
    // een oneindige sequence: alleen de gevraagde elementen worden berekend
    val powersOfTwo = generateSequence(1) { it * 2 }
    val firstOnes = powersOfTwo.transform { "2^${it.countTrailingZeroBits()}=$it" }.take(5)
    println("powers of 2: ${firstOnes.toList()}")
}

// filtert een lijst met een predicaat: het werk dat filter doet
inline fun <T> List<T>.filterBy(predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in this) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

fun isOdd(n: Int) = n % 2 != 0

// een tussenbewerking op een sequence die alleen de elementen doorlaat die aan het predicaat voldoen
fun <T> Sequence<T>.keep(predicate: (T) -> Boolean): Sequence<T> = sequence {
    for (element in this@keep) {
        if (predicate(element)) yield(element)
    }
}

// een tussenbewerking die elk element transformeert: het equivalent van map
fun <T, R> Sequence<T>.transform(transformation: (T) -> R): Sequence<R> = sequence {
    for (element in this@transform) {
        yield(transformation(element))
    }
}

    7.8. Expressiebomen

    Sommige talen, zoals C#, staan toe dat een lambda niet wordt omgezet naar uitvoerbare code, maar naar een gegevensstructuur die haar beschrijft (een „expressieboom"): een programma kan de lambda [t => t.Limit > 20000] dan analyseren en bijvoorbeeld vertalen naar een SQL-clausule [WHERE limits > 20000] die door de databaseserver wordt uitgevoerd.

    Kotlin heeft, net als Java, geen equivalent: een Kotlin-lambda wordt altijd gecompileerd tot uitvoerbare code; ze kan worden aangeroepen, maar haar interne werking kan niet worden onderzocht. Verschillende hulpmiddelen komen er echter in de buurt:

    • Eigenschapsreferenties: [Person::age] is een object ([KProperty1<Person, Int>]) dat de naam van de eigenschap ([Person::age.name]) en haar type kent. Een bibliotheek kan dit gebruiken om een query op te bouwen zonder een tekenreeks te schrijven: dit is wat Spring Data MongoDB bijvoorbeeld doet met zijn Kotlin-extensies, waarmee u een criterium kunt schrijven als [Person::age gt 18];
    • Interne DSL's („Domain-Specific Languages"): dankzij lambda's met receivers, [infix]-functies en operatoroverloading kan een Kotlin-bibliotheek een syntaxis bieden die op SQL lijkt en die het programma uitvoert om een gegevensstructuur op te bouwen die de query beschrijft. Dit is het principe achter de bibliotheek Exposed van JetBrains: [Brackets.selectAll().where { Brackets.limit greater 20000 }];
    • compilerplug-ins: de Kotlin-compiler kan worden uitgebreid met plug-ins die de code transformeren. Zo werkt kotlinx.serialization, net als de plug-ins [all-open] en [no-arg] die met Spring en Hibernate worden gebruikt, of de plug-in [power-assert], die de expressie van een assertie analyseert om bij een mislukking de details ervan te tonen. Dit zijn echter ontwikkelhulpmiddelen en geen ingebouwde functies van het programma.

    Hibernate, dat we in hoofdstuk 11 behandelen, biedt dezelfde oplossingen als in Java: een querytaal die op SQL lijkt maar is uitgedrukt in klassen en eigenschappen, HQL (["from Bracket t where t.limit > 20000"]), en de Criteria-API van Jakarta Persistence , die de query opbouwt via methodeaanroepen ([cb.gt(t.get("limit"), 20000)]). In beide gevallen is de query gegevens (een tekenreeks of een objectboom) die Hibernate vertaalt naar SQL, terwijl een lambda die aan [filter] wordt doorgegeven, binnen het Kotlin-programma wordt uitgevoerd.

    7.9. Conclusie

    De belangrijkste punten van dit hoofdstuk:

    • in Kotlin zijn functies waarden: ze hebben een functietype ([(Int, Int) -> Int], [() -> Unit], [(T) -> Boolean], [(() -> Unit)?], [T.() -> R]…), kunnen in variabelen worden opgeslagen, als parameter worden doorgegeven, als resultaat worden geretourneerd en worden aangeroepen als gewone functies. Voor de virtuele machine zijn het objecten die de interfaces [Function0], [Function1]… implementeren;
    • de interfaces van [java.util.function] ([Function], [Supplier], [Consumer], [Predicate]…), samen met [Runnable], [Callable] en [Comparator], blijven bruikbaar: wanneer een Java-methode een functionele interface verwacht, zet Kotlin een lambda of een referentie er automatisch naar om (SAM-conversie); elders wordt de conversie expliciet geschreven: [Comparator { … }];
    • om een functietype een naam te geven, hebben we de alias [typealias] (slechts een alias) en [fun interface] (een echt nieuw type, te implementeren via een lambda);
    • een functie kan worden verkregen via een lambda-expressie ([{ a, b -> a + b }], [{ it * it }], buiten haakjes geschreven wanneer ze de laatste parameter is, en afgesloten met [return@label]), via een anonieme functie, via een anoniem object of via een referentie ([::function], [object::method], [Class::method], [::Class]). Twee referenties naar dezelfde functie van hetzelfde object zijn gelijk; twee lambda's zijn nooit gelijk;
    • lambda's leggen de variabelen vast die hen omringen, waaronder de [var], die ze kunnen wijzigen (de compiler slaat ze op in [Ref]-objecten); ze zien dan de waarde van de variabele op het moment van hun uitvoering, wat voorzichtigheid vereist in lussen en tussen threads;
    • functies die functies retourneren en extensies op functionele typen ([then], [and], [or]…) stellen nieuwe functies samen; [compareBy], [thenBy] en [reversed] bouwen comparators op;
    • de functies [inline] kopiëren hun code en die van de lambda's naar de aanroepplaats, zonder object of conversie, en staan niet-lokale returns toe; [noinline] en [crossinline] behandelen bijzondere gevallen. De scopefuncties [let], [run], [with], [apply] en [also] zijn de meest gebruikelijke toepassingen hiervan;
    • een functietype wordt gekozen voor kortstondig, eenmalig gedrag; een [fun interface] voor een apart type of een API die vanuit Java kan worden gebruikt; een interface met meerdere leden (of een „zakelijke" interface) voor een rol in de applicatie;
    • een gebeurtenis wordt ingericht met het listenerpatroon: een klasse [XxxEvent], een listenertype (vaak een [typealias] voor een functietype), [addXxxListener] / [removeXxxListener], en een lijst met functies ([CopyOnWriteArrayList]) die door een methode [fireXxx] wordt doorlopen. De gedelegeerde eigenschappen [Delegates.observable] en [Delegates.vetoable] melden of filteren wijzigingen van een eigenschap, en [PropertyChangeSupport] beheert voor hen de lijst met listeners;
    • bewerkingen op collecties (onmiddellijk, [inline]) en sequentiebewerkingen (lui) zijn hogere-ordefuncties; Kotlin kent geen expressiebomen, en Hibernate drukt zijn queries uit met HQL of de Criteria-API.

    Lambda's komen in alle volgende hoofdstukken terug: een thread voert een lambda uit ([thread { … }]), en een [ExecutorService] voert een [Callable] uit (hoofdstuk 8); een coroutine wordt gestart met [launch { … }] of [async { … }] (hoofdstuk 9), extensiefuncties van [ResultSet] ontvangen in de vorm van een lambda de transformatie van een regel uit het resultaat naar een object (hoofdstuk 10), en Spring Boot-webservices verwerken HTTP-verzoeken in methoden die het framework als listeners aanroept (hoofdstuk 13).
