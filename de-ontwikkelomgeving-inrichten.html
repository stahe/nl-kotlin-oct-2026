    2. De ontwikkelomgeving inrichten

    De werkomgeving van de Kotlin-ontwikkelaar bestaat uit drie onafhankelijke onderdelen:

    • de JDK (“Java Development Kit”): Kotlin, zoals we het in dit document gebruiken, wordt gecompileerd tot bytecode en uitgevoerd door de Java Virtual Machine (JVM), net als een Java-programma. De JDK levert deze virtuele machine, het commando [java] dat programma’s uitvoert, de standaardbibliotheken van Java SE (die Kotlin rechtstreeks gebruikt: bestanden, netwerk, datums, threads enzovoort) en hulpmiddelen zoals [javap] of [jar];
    • een buildtool voor projecten, hier Gradle: die downloadt de Kotlin-compiler en de bibliotheken die een project nodig heeft, compileert het project, voert de tests uit en verpakt het;
    • een editor of een IDE (Integrated Development Environment): [IntelliJ IDEA], ontworpen door het bedrijf dat Kotlin heeft gemaakt, is de voor de hand liggende keuze; [VS Code] met de Kotlin-extensie is een alternatief. De IDE steunt op de JDK en kan Gradle-projecten lezen.

    De Kotlin-compiler zelf staat niet in dit lijstje: Gradle downloadt hem voor elk project en IntelliJ IDEA bevat hem. U kunt hem echter apart installeren met het commando [kotlinc] om één enkel bestand te compileren: dat doen we voor ons eerste programma, maar het is optioneel.

    Dit document gebruikt de commando’s [java], [kotlinc] en [gradlew] voor alle handelingen: ze werken op Windows, Linux en macOS op dezelfde manier, ongeacht de editor die u kiest.

    2.1. JDK 25

    2.1.1. Installatie

    Er bestaan meerdere distributies van de JDK, allemaal gebouwd uit de broncode van OpenJDK en voor ons doel gelijkwaardig. Wij raden Eclipse Temurin aan, een gratis opensourcedistributie van de Eclipse Foundation, te downloaden op https://adoptium.net: kies daar versie 25 (LTS), het besturingssysteem en het pakkettype (op Windows een installatieprogramma van het type [.msi]). Op Windows kunt u de JDK ook installeren vanuit een terminal (PowerShell of opdrachtprompt) met de pakketbeheerder [winget]:

    1
    winget install EclipseAdoptium.Temurin.25.JDK

    U moet de JDK kiezen (die alles bevat) en niet alleen de JRE (waarmee u uitsluitend vooraf gecompileerde programma’s kunt uitvoeren). Vink bij de installatie op Windows de opties aan die de JDK toevoegen aan [PATH] en de omgevingsvariabele [JAVA_HOME] instellen: Gradle, de compiler [kotlinc] en de IDE gebruiken die om de JDK te vinden. Op Linux is de JDK beschikbaar in de repositories van de grote distributies (bijvoorbeeld [sudo apt install openjdk-25-jdk] op Ubuntu).

    Open na de installatie een nieuwe terminal om te controleren of het commando [java] beschikbaar is en de versie van de JDK weergeeft:

    1
2
3
4
    > java --version
openjdk 25.0.4 2026-07-21 LTS
OpenJDK Runtime Environment Temurin-25.0.4+7 (build 25.0.4+7-LTS)
OpenJDK 64-Bit Server VM Temurin-25.0.4+7 (build 25.0.4+7-LTS, mixed mode, sharing)

    Deze resultaten zijn verkregen met JDK Temurin 25.0.4, die bij het schrijven van dit document is gebruikt. De exacte versie hangt af van de installatiedatum: elk kwartaal verschijnen bugfixupdates. Alle versies 25.0.x van de JDK zijn geschikt voor dit document. Meerdere JDK’s kunnen naast elkaar op dezelfde computer staan: de eerste die in [PATH] wordt gevonden, beantwoordt het commando [java].

    De JDK bevat ook de Java-compiler [javac] ([javac --version] toont [javac 25.0.4]). We hebben hem niet nodig: de Kotlin-compiler genereert de bytecode zelf. Maar hij is er, en een Gradle-project kan Kotlin- en Java-bestanden gemakkelijk combineren, die samenwerken.

    2.1.2. De commando’s van de JDK

    Dit zijn de commando’s van de JDK die we gebruiken:

    Commando
    Functie
    [java -jar program.jar]
    Voert het programma uit dat zich in een [.jar]-archief bevindt waarvan het manifest de hoofdklasse aangeeft
    [java -cp classes MyClass]
    voert de functie [main] van een gecompileerde klasse uit, die wordt gezocht in het klassenpad ([-cp], “class path”)
    [javap -cp classes MyClass]
    toont de members van een gecompileerde klasse: hiermee zien we wat de Kotlin-compiler heeft geproduceerd
    [jar]
    maakt of leest een [.jar]-archief (een zipbestand met gecompileerde klassen)

    De JDK levert ook de interactieve interpreter [jshell], maar die accepteert alleen Java-instructies. Gebruik om een Kotlin-expressie te testen zonder een programma te schrijven liever de hieronder beschreven hulpmiddelen van IntelliJ IDEA.

    2.2. De Kotlin-opdrachtregelcompiler

    2.2.1. Installatie

    Deze installatie is optioneel: Gradle-projecten hebben haar niet nodig en IntelliJ IDEA bevat een eigen compiler. Hiermee kunt u vanuit een terminal een zelfstandig Kotlin-bestand compileren en uitvoeren zonder een project aan te maken.

    De compiler kunt u downloaden van de pagina met releases van het Kotlin-project op GitHub (https://github.com/JetBrains/kotlin/releases): download in de sectie “Assets” van versie 2.4.20 het archief [kotlin-compiler-2.4.20.zip]. Pak het uit in een map, bijvoorbeeld [C:\Program Files\kotlinc], en voeg de submap [bin] toe aan [PATH] (Windows: “Systeemomgevingsvariabelen bewerken”). U kunt ook een pakketbeheerder gebruiken: [scoop install kotlin] op Windows (met Scoop), of SDKMAN! op Linux en macOS ([sdk install kotlin 2.4.20]). De compiler heeft een JDK nodig, die hij vindt via de variabele [JAVA_HOME] of de variabele [PATH].

    Controleer de installatie in een nieuwe terminal:

    1
2
    > kotlinc -version
info: kotlinc-jvm 2.4.20 (JRE 25.0.4+7-LTS)

    Op het versienummer van de compiler (2.4.20) volgt de versie van de JVM die hem uitvoert (JDK 25).

    2.2.2. Compilercommando’s

    De map [bin] bevat twee hoofdcommando’s, [kotlinc] (de compiler) en [kotlinr] (de launcher, “runner”):

    Commando
    Functie
    [kotlinc File.kt -d classes]
    compileert een of meer bronbestanden en plaatst de resulterende [.class]-bestanden in de map [classes]
    [kotlinc File.kt -include-runtime -d prog.jar]
    compileert en maakt een uitvoerbaar archief met de naam [.jar], dat ook de Kotlin-standaardbibliotheek bevat
    [kotlinr -cp classes MyClass]
    als [java -cp classes MyClass], maar met de Kotlin-standaardbibliotheek toegevoegd aan het klassenpad
    [kotlinr script.main.kts]
    voert een Kotlin-script uit (bestand [.main.kts]), zonder zichtbare compilatiestap

    Een Kotlin-script is een reeks instructies die van boven naar beneden wordt uitgevoerd, zonder functie [main]. Het volgende script [essai.main.kts] bijvoorbeeld:

    1
2
    val s = "Kotlin " + 2.4
println(s.length)

    wordt als volgt uitgevoerd:

    1
2
    > kotlinr essai.main.kts
10

    Vóór Kotlin 2.4.20 heette de launcher [kotlin]; in Kotlin 2.4.20 is hij hernoemd naar [kotlinr] om een naamconflict te voorkomen met een ander commando, [kotlin], dat bij de tool “Kotlin Toolchain” hoort. De oude naam werkt nog in versie 2.4.20 van de compiler (hij is niet officieel verouderd), maar de Kotlin-documentatie raadt nu [kotlinr] aan.

    Zonder argumenten startte het commando [kotlinc] vroeger een interactieve interpreter (een “REPL”, vergelijkbaar met [jshell]). Deze functie is inmiddels verouderd:

    1
2
    > kotlinc
error: Kotlin REPL is deprecated and should be enabled explicitly for now; please use the '-Xrepl' option

    Om een paar regels Kotlin uit te proberen, kunt u beter een scratchbestand gebruiken, aangemaakt met IntelliJ IDEA (“File / New / Scratch File”, taal Kotlin), dat de resultaten naast elke regel toont.

    2.3. Gradle

    2.3.1. De rol van Gradle

    Een echte applicatie gebruikt bibliotheken die geen deel uitmaken van de JDK of de Kotlin-standaardbibliotheek: een databasestuurprogramma, een testframework, Hibernate, Spring, coroutines… Ze worden verspreid als [.jar]-archieven via een openbare repository, Maven Central (https://central.sonatype.com). Een buildtool leest de beschrijving van het project om te bepalen welke bibliotheken nodig zijn, downloadt ze (samen met de bibliotheken waarvan ze afhangen) en compileert, test en verpakt daarna het project.

    De twee grote buildtools in de Java-wereld zijn Maven (gebruikt in de Java-cursus waarop dit document is gebaseerd) en Gradle. Kotlin kan met beide worden gebruikt, maar Gradle is de de-factostandaard in het Kotlin-ecosysteem: Android gebruikt het, evenals de Kotlin-projecten die IntelliJ IDEA aanmaakt, en de buildbestanden zijn geschreven in… Kotlin. Dit document gebruikt Gradle 9.8.

    2.3.2. De Gradle-wrapper: geen installatie nodig

    U hoeft Gradle niet te installeren. Elk project in dit document wordt geleverd met de Gradle-wrapper, een kleine launcher die uit drie bestanden in de hoofdmap van het project bestaat:

    • [gradlew]: het startscript voor Linux en macOS ([./gradlew]);
    • [gradlew.bat]: hetzelfde script voor Windows ([gradlew]);
    • de map [gradle/wrapper], die het launcherprogramma ([gradle-wrapper.jar]) en de configuratie ervan ([gradle-wrapper.properties]) bevat.

    Het bestand [gradle-wrapper.properties] geeft aan welke Gradle-versie moet worden gebruikt:

    1
    distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.0-bin.zip

    De eerste keer dat [gradlew] wordt uitgevoerd, downloadt het deze versie van Gradle en slaat die op de computer op; bij volgende keren gebruikt het die rechtstreeks. Elk project gebruikt dus de Gradle-versie waarmee het is geschreven, ongeacht welke versie er op de computer is geïnstalleerd. Gradle heeft alleen een JDK nodig om te draaien, die het vindt via de variabele [JAVA_HOME] of de variabele [PATH].

    In dit document worden commando’s geschreven in de Windows-notatie ([gradlew build]); op Linux of macOS schrijft u [./gradlew build]. In PowerShell moet u ook [.\gradlew build] schrijven.

    Als u toch het commando [gradle] wilt gebruiken (bijvoorbeeld om een project aan te maken met [gradle init]), download dan het archief [gradle-9.8.0-bin.zip] van https://gradle.org/releases, pak het uit en voeg de submap [bin] toe aan [PATH]; of gebruik [scoop install gradle] of [sdk install gradle].     2.3.3. Gradle-commando’s

    Het commando [gradlew] wordt gevolgd door een of meer taken; u voert het in in de hoofdmap van het project, de map die het bestand [settings.gradle.kts] bevat:

    Commando
    Functie
    [gradlew build]
    compileert de broncode in [src/main/kotlin], voert de tests uit en maakt het projectarchief [.jar] aan in [build/libs]
    [gradlew run]
    compileert en voert daarna de hoofdklasse van het project uit (plug-in [application])
    [gradlew test]
    compileert en voert daarna de unittests in [src/test/kotlin] uit (hoofdstuk 6)
    [gradlew clean]
    verwijdert de map [build]
    [gradlew tasks]
    toont de lijst met beschikbare taken in het project
    [gradlew installDist]
    maakt in [build/install] een installeerbare versie van het programma aan: de archieven en startscripts ervan
    [gradlew bootRun]
    voert een Spring Boot-applicatie uit (hoofdstuk 13)

    De taken zijn van elkaar afhankelijk: [run] uitvoeren activeert ook de compilatie, en Gradle voert alleen de onderdelen opnieuw uit die sinds de vorige build zijn gewijzigd. De optie [-q] (“quiet”) onderdrukt de berichten van Gradle en toont alleen die van het uitgevoerde programma; de optie [-Pname=value] stelt een property in die het buildbestand kan lezen: daarmee kiezen we welk programma wordt uitgevoerd. De argumenten voor het programma dat door [run] wordt gestart, geeft u mee via de optie [--args="a b"].

    Het eerste commando dat in een project wordt uitgevoerd, is traag: Gradle start een achtergrondproces (de Gradle-“daemon”), dat enkele uren actief blijft om volgende commando’s te versnellen, en downloadt wat het project nodig heeft.

    2.3.4. Maven Central en de Gradle-cache

    De bibliotheken die Gradle downloadt, worden lokaal opgeslagen in de cache van Gradle, in de map [%USERPROFILE%\.gradle\caches] (Linux en macOS: [~/.gradle/caches]). Ze worden maar één keer gedownload en daarna door alle projecten hergebruikt. Bij de eerste build van een project is dus een internetverbinding nodig. Dezelfde map [.gradle] bevat in [wrapper/dists] de Gradle-versies die de wrapper heeft gedownload.

    Een bibliotheek wordt geïdentificeerd door haar coördinaten: drie namen gescheiden door dubbele punten: de groep (vaak een omgekeerde domeinnaam, zoals [org.hibernate.orm]), de naam van de bibliotheek en de versie ervan, bijvoorbeeld [tools.jackson.core:jackson-databind:3.1.5]. Deze coördinaten voert u in het buildbestand van een project in en u vindt ze door op de website van Maven Central naar de bibliotheek te zoeken.

    2.3.5. De Kotlin-syntaxis: DSL

    Het buildbestand van het project heet [build.gradle.kts]. De extensie [.kts] geeft aan dat het een Kotlin-script is: het bestand is geschreven in een specifieke taal (“DSL”, “Domain Specific Language”) die op de syntaxis van Kotlin is gebouwd. Gradle ondersteunt ook bestanden [build.gradle] in Groovy, die u in oudere projecten aantreft; sinds Gradle 8.2 is de Kotlin-DSL het standaardformaat. Hier is een typisch fragment:

    1
2
3
4
5
6
7
8
    plugins {
    kotlin("jvm") version "2.4.20"
    application
}

dependencies {
    implementation("tools.jackson.core:jackson-databind:3.1.5")
}

    Ook zonder Kotlin al te kennen kunt u deze tekst als een configuratie lezen:

    • een naam gevolgd door een blok tussen accolades ([plugins { ... }], [dependencies { ... }]) is een sectie van de configuratie. In Kotlin is dit een functieaanroep die een codeblok als parameter neemt (een lambda, hoofdstuk 7);
    • [kotlin("jvm")] en [implementation("...")] zijn functieaanroepen; de strings staan tussen dubbele aanhalingstekens;
    • [version = "1.0"] kent een waarde toe aan een property van het project.

    Een voordeel van dit formaat is dat IntelliJ IDEA het als Kotlin-code herkent: het biedt codeaanvulling en markeert fouten terwijl u typt.

    2.4. De editor

    2.4.1. IntelliJ IDEA

    IntelliJ IDEA, van het bedrijf JetBrains, is de aanbevolen editor voor dit document. JetBrains is ook het bedrijf dat Kotlin heeft ontwikkeld (de eerste stabiele versie van de taal verscheen in 2016) en dat de taal blijft ontwikkelen: de ondersteuning voor Kotlin is ingebouwd in IntelliJ IDEA, zonder extensies, en volgt de evolutie van de taal het dichtst. De basisfuncties, die ruim voldoende zijn voor dit document, zijn gratis.

    IntelliJ IDEA herkent Gradle-projecten: kies “File / Open” en selecteer vervolgens de map die het bestand [settings.gradle.kts] bevat; IntelliJ start Gradle om het project te lezen (u kunt het proces volgen in het venster “Build”), downloadt de bibliotheken en toont dan een weergave “Gradle” die toegang geeft tot alle taken van het project. Vervolgens kunt u een programma uitvoeren door op de groene driehoek in de marge naast de functie [main] te klikken ([Ctrl-Shift-F10]), of een test uitvoeren door op dezelfde driehoek naast de testfunctie te klikken. De te gebruiken JDK geeft u op via “File / Project Structure / SDK”; bij een Gradle-project is het meestal de declaratie [jvmToolchain(25)] van het project (zie hieronder) die de JDK voor de compilatie bepaalt.

    IntelliJ IDEA biedt ook functies die specifiek zijn voor Kotlin: automatische conversie van een Java-bestand naar Kotlin (“Code / Convert Java File to Kotlin File”, of gewoon door Java-code in een Kotlin-bestand te plakken), weergave van de bytecode die de compiler heeft gegenereerd (“Tools / Kotlin / Show Kotlin Bytecode”) en de eerder genoemde scratchbestanden.

    2.4.2. VS Code

    VS Code is een gratis, platformonafhankelijke editor. Om in Kotlin te programmeren installeert u de extensie Kotlin van JetBrains (ga naar het menu “Extensions”, zoek op “Kotlin” en kies de extensie waarvan JetBrains de uitgever is). Deze officiële extensie is nieuw: ze gebruikt dezelfde code-analyse-engine als IntelliJ IDEA en kan Gradle-projecten importeren, maar biedt nog niet alle functies van de IDE van JetBrains en haar functionaliteit verandert van versie tot versie. Raadpleeg de pagina van de extensie om te zien wat ze ondersteunt op het moment van installatie. Voor dit document is ze geschikt om programma’s te lezen en te bewerken; u kunt ze altijd uitvoeren vanuit de ingebouwde terminal (“Terminal / New Terminal”) met de [gradlew]-commando’s uit de tekst.

    Open in VS Code de map van een hoofdstuk (“File / Open Folder”), bijvoorbeeld de map [kotlin-oct-2026/03-basics].

    2.4.3. Android Studio

    Kotlin is ook de taal die Google aanbeveelt voor Android-apps. Android Studio, gebouwd op IntelliJ IDEA, is bedoeld voor dit soort apps, die in dit document niet aan bod komen.

    In de rest van dit document worden de handelingen beschreven met de commando’s [java], [kotlinc] en [gradlew], die ongeacht de editor dezelfde resultaten geven.

    2.5. Een voorbeeldprogramma: het bestand Hello.kt

    2.5.1. Het programma

    Een Kotlin-programma kan een eenvoudig bestand zijn met een functie met de naam [main], zonder klassedeclaratie. We maken het volgende bestand [Hello.kt] (in de map [02-installation] met voorbeelden):

    1
2
3
4
    // eerste Kotlin-programma: een top-level functie main
fun main() {
    println("1st try with Kotlin 2.4")
}

    Toelichting:

    • regel 1: een commentaarregel. Alles na [//] tot het einde van de regel wordt door de compiler genegeerd;
    • regel 2: de functie [main], het startpunt van het programma. Het sleutelwoord [fun] introduceert een functie. Ze is op bestandsniveau gedeclareerd (“top-level function”), buiten elke klasse; ze hoeft niet als [public] te worden gedeclareerd (dat is in Kotlin de standaardzichtbaarheid) en hoeft ook geen programma-argumenten te ontvangen;
    • regel 3: de enige instructie van het programma: ze toont een regel tekst op het scherm. De functie [println] (en [print], die niet naar de volgende regel gaat) maakt deel uit van de Kotlin-standaardbibliotheek; ze is het equivalent van [System.out.println] in Java. Merk op dat er aan het einde van de instructie geen puntkomma staat: die is in Kotlin optioneel en wordt niet geschreven.

    Het programma is iets eenvoudiger dan zijn equivalent in de Java-cursus ([void main() { IO.println(...); }]), maar het echte verschil zit elders: de top-level functie [main] bestaat in Kotlin sinds de eerste release, terwijl Java haar pas sinds Java 25 ondersteunt.

    2.5.2. Compilatie en uitvoering

    We compileren het programma met [kotlinc] en geven een uitvoerbaar archief met de naam [.jar] op, waarna we het uitvoeren met het commando [java] van de JDK:

    1
2
3
    > kotlinc Hello.kt -include-runtime -d hello.jar
> java -jar hello.jar
1st try with Kotlin 2.4
    • [-d hello.jar]: de bestemming van de compilatie. Als die op [.jar] eindigt, maakt de compiler een archief; anders is het een map waarin hij de [.class]-bestanden opslaat;
    • [-include-runtime]: het archief bevat ook de Kotlin-standaardbibliotheek ([kotlin-stdlib]), die Kotlin-programma’s tijdens de uitvoering nodig hebben, en een manifest dat de hoofdklasse aangeeft. Het programma kan zo met [java -jar] worden uitgevoerd op elke machine met een JDK (of JRE), ook als Kotlin op die machine niet is geïnstalleerd. Het archief is daarentegen meer dan 5 MB groot, grotendeels door de standaardbibliotheek;
    • de compilatie duurt enkele seconden: de Kotlin-compiler, zelf een Java-programma, moet eerst opstarten. Gradle en IntelliJ IDEA vermijden deze overhead door tussen compilaties een compiler actief te houden.

    In Kotlin bestaat geen equivalent van het Java-commando [java Hello.java], dat een bronbestand in één stap compileert en uitvoert; het dichtstbijzijnde equivalent is het hierboven besproken [.main.kts]-script.

    2.5.3. Wat de compiler produceert

    De Java Virtual Machine (JVM) herkent alleen klassen: een functie kan niet buiten een klasse bestaan. De Kotlin-compiler verpakt de top-level functies van een bestand daarom in een klasse die hij zelf genereert en die hij naar het bestand noemt: de bestandsnaam gevolgd door [Kt]. Voor [Hello.kt]is de gegenereerde klasse [HelloKt]. Het commando [javap] van de JDK toont de members ervan:

    1
2
3
4
5
6
    > javap -cp hello.jar HelloKt
Compiled from "Hello.kt"
public final class HelloKt {
  public static final void main();
  public static void main(java.lang.String[]);
}
    • De klasse [HelloKt] is [public final];
    • ze bevat onze functie [main], die een statische methode zonder parameters is geworden;
    • en een tweede methode, [main(String[])], die de compiler heeft toegevoegd: dit is de methode [public static void main(String[] args)] die de virtuele machine weet aan te roepen. Ze roept eenvoudig de eerste aan. We komen op dit mechanisme terug in hoofdstuk 3.

    Deze klassenaam identificeert het uit te voeren programma: het manifest van [hello.jar] bevat de regel [Main-Class: HelloKt], en u kunt ook [java -cp hello.jar HelloKt]schrijven.

    Anders dan in Java gelden er geen beperkingen voor de bestandsnaam: die hoeft geen geldige identifier te zijn of overeen te komen met de naam van een klasse die erin staat. Een bestand met de naam [first-try.kt] wordt geaccepteerd en de gegenereerde klasse heet [First_tryKt] (de compiler zet de eerste letter als hoofdletter en vervangt tekens die in een identifier niet zijn toegestaan door [_]). Volgens afspraak geeft men bestanden echter namen die met een hoofdletter beginnen en geen koppeltekens bevatten, zoals [Hello.kt] of [Basics01.kt].

    Op Windows worden letters met accenten die met [println] worden geschreven correct in de terminal weergegeven: de virtuele machine zet de tekst om naar de codering van de terminal. Bronbestanden moeten in UTF-8 worden opgeslagen, de standaardcodering van VS Code en IntelliJ IDEA en de codering die de Kotlin-compiler altijd veronderstelt. De situatie is anders wanneer het programma door Gradle wordt gestart ([gradlew run], of de groene driehoek in een Gradle-project): de uitvoer gaat dan niet meer naar een console maar via een pipe naar Gradle, en de virtuele machine codeert die dan in de historische Windows-codering (windows-1252), zodat IntelliJ IDEA, dat UTF-8 verwacht, in plaats van elk teken met een accent een vervangend teken toont (een ruit met een vraagteken). De cursusprojecten lossen dit probleem op in hun bestand [build.gradle.kts] (zie de volgende paragraaf). In de ingebouwde terminal van IntelliJ IDEA (PowerShell) kunt u de console ook naar UTF-8 omschakelen door aan het begin van de sessie [chcp 65001] te typen, of voorgoed door [powershell.exe -NoExit -Command "[Console]::OutputEncoding = [Text.Encoding]::UTF8"] als interpreter op te geven onder “File / Settings / Tools / Terminal / Shell path”.

    Het commando [kotlinc] is geschikt voor programma’s uit één bestand die alleen de standaardbibliotheek gebruiken. Zodra een programma een externe bibliotheek nodig heeft, moet u die downloaden, samen met de bibliotheken waarvan ze afhangt, en aan de compiler en daarna aan de virtuele machine doorgeven: dat betekent een Gradle-project aanmaken. Dat doen we voor alle voorbeelden in dit document.

    • regels 18–20: de bibliotheken die het project gebruikt. Dit project gebruikt er geen, afgezien van de Kotlin-standaardbibliotheek die de Kotlin-plug-in automatisch toevoegt;
    • regel 24: de toolchain van het project: de code wordt gecompileerd voor Java 25 en door [gradlew run] uitgevoerd met een JDK 25, ook al draait Gradle zelf met een andere JDK. Gradle zoekt deze JDK onder de JDK’s die op de machine zijn geïnstalleerd. Vindt het er geen, dan mislukt het met de foutmelding [Cannot find a Java installation on your machine ... matching: {languageVersion=25 ...}], tenzij de build de plug-in [foojay-resolver-convention] declareert, wat alle projecten van de cursus doen (zie de volgende paragraaf): Gradle downloadt dan zelf een JDK 25. In IntelliJ IDEA kunt u deze JDK ook installeren via “File / Project Structure / SDK / Add SDK / Download JDK”;
    • regel 27: een compilerwaarschuwing wordt als fout behandeld en stopt de compilatie. De Kotlin-compiler signaleert veel problemen (ongebruikte variabelen, overbodige typecasts, overbodige [!!]-operatoren enzovoort): we willen programma’s die er geen produceren;
    • regel 29: de compiler bewaart de namen van de functieparameters in de bytecode. Sommige bibliotheken maken hiervan gebruik, bijvoorbeeld Jackson om een object uit een JSON-document te maken (hoofdstuk 5) of Spring (hoofdstuk 13);
    • regels 33–35: de klasse waarvan de functie [main] door [gradlew run] wordt uitgevoerd. De naam is die van de klasse die de compiler voor het bestand [Main.kt] in de package [first] genereert: [first.MainKt];
    • regels 38–41: alle taken die een Java-programma uitvoeren ([JavaExec]), zoals [run], krijgen twee opties van de virtuele machine mee: de schermuitvoer van het programma ([System.out], [System.err]) wordt in UTF-8 gecodeerd. Zonder deze opties zouden letters met accenten die het programma schrijft, onder Windows in de console van IntelliJ IDEA onleesbaar worden (zie de opmerking over accenten hierboven). [tasks.withType<JavaExec>()] verwijst naar alle taken van dit type en [configureEach { … }] configureert elk ervan. Alle cursusprojecten die een programma uitvoeren, bevatten deze configuratie.

    2.6.2. Compilatie en uitvoering

    Het commando [gradlew build], ingevoerd in de map [02-installation], compileert de projecten van de build (en zou hun tests uitvoeren als ze die hadden): Gradle downloadt zo nodig de Kotlin-plug-in, de compiler en de standaardbibliotheek, compileert vervolgens de bestanden in [src/main/kotlin] en plaatst de resulterende klassen per project in de map [build/classes/kotlin/main], met behoud van de packagestructuur ([FirstProgram/build/classes/kotlin/main/first/MainKt.class]).

    Het commando [gradlew run] compileert een project en voert het daarna uit. In een build met meerdere projecten geeft u het project op met zijn pad, voorafgegaan door een dubbele punt: [:FirstProgram:run] is de taak [run] van het project [FirstProgram]. Met de optie [-q]wordt alleen de uitvoer van het programma getoond:

    1
2
    > gradlew -q :FirstProgram:run
1st try with a Gradle / Kotlin 2.4 project

    U kunt ook naar de projectmap gaan en [..\gradlew -q run]typen: Gradle zoekt dan het bestand [settings.gradle.kts] in de hoofdmap op en voert de taak [run] van het project in de huidige map uit. Als u daarentegen [gradlew run] in de hoofdmap typt, wordt de taak [run] uitgevoerd voor alle projecten die er een hebben.

    Zodra het project is gecompileerd, kunt u de klasse ook rechtstreeks uitvoeren met het commando [java], waarbij u de locatie van de klassen opgeeft (in de map [FirstProgram]):

    1
2
    > java -cp build/classes/kotlin/main first.MainKt
1st try with a Gradle / Kotlin 2.4 project

    Dit werkt hier omdat dit programma tijdens de uitvoering niets uit de Kotlin-standaardbibliotheek gebruikt: de compiler vervangt de aanroep van [println] door een directe aanroep van [System.out.println]. Een programma dat bijvoorbeeld een lijst gebruikt ([listOf(1, 2, 3)]) mislukt op deze manier met de fout [java.lang.NoClassDefFoundError: kotlin/collections/CollectionsKt]: de klasse [CollectionsKt] van de standaardbibliotheek wordt niet gevonden. U moet dan het archief [kotlin-stdlib-2.4.20.jar] aan het klassenpad toevoegen (het staat in de Gradle-cache; de map [lib] van de compiler [kotlinc] bevat het ook, onder de naam [kotlin-stdlib.jar]): [java -cp "build/classes/kotlin/main;path/kotlin-stdlib-2.4.20.jar" first.MainKt] op Windows (het scheidingsteken is [:] op Linux en macOS). Het commando [kotlinr -cp build/classes/kotlin/main first.MainKt] van de opdrachtregelcompiler doet dit voor ons.

    Het eenvoudigst is om Gradle het programma en alles wat het nodig heeft te laten bouwen met de taak [installDist] van de plug-in [application]:

    1
    > gradlew -q :FirstProgram:installDist

    Dit maakt de map [FirstProgram/build/install/FirstProgram] aan, die een map [lib] bevat (het projectarchief, de Kotlin-standaardbibliotheek en eventueel de andere bibliotheken van het project) en een map [bin] met twee startscripts, [FirstProgram] (Linux, macOS) en [FirstProgram.bat] (Windows), die [java] met het juiste klassenpad aanroepen. In deze vorm wordt een programma geleverd om het naar een andere computer met een JDK te kopiëren:

    1
2

1st try with a Gradle / Kotlin 2.4 project

    De map [build] kan zonder bezwaar worden verwijderd ([gradlew clean]): ze wordt bij de volgende compilatie opnieuw aangemaakt. Het commando [gradlew build] maakt ook het archief van het project aan, [build/libs/FirstProgram-1.0.jar], dat alleen de eigen klassen bevat.

    2.7.3. Eén package per programma

    De projecten in de volgende hoofdstukken gebruiken allemaal dit mechanisme, omdat ze elk veel kleine programma’s bevatten. Om te voorkomen dat deze programma’s elkaar storen, volgt dit document een eenvoudige afspraak: elk programma heeft zijn eigen package, die zijn naam in kleine letters draagt en is opgeslagen in een map met dezelfde naam. Zo is het programma [Basics04.kt] uit hoofdstuk 3 het bestand [03-basics/src/main/kotlin/basics04/Basics04.kt], dat begint met de regel [package basics04]; de klasse ervan is [basics04.Basics04Kt]en het wordt als volgt uitgevoerd:

    1
    gradlew -q run -Pmain=basics04.Basics04Kt

    Er zijn twee redenen voor deze afspraak:

    • alle programma’s van een project worden samen gecompileerd. Stonden ze in dezelfde package, dan zouden twee programma’s geen functie of klasse met dezelfde naam kunnen declareren (een functie [display], een klasse [Person]…): de compiler zou een dubbele declaratie melden. Met één package per programma heeft elk zijn eigen naamruimte;
    • een programma dat uit meerdere bestanden bestaat, is gewoon een package met meerdere bestanden: in hoofdstuk 4 bevat de package [persons] de klasse [Person] in [Person.kt] en het hoofdprogramma in [Main.kt], dat wordt uitgevoerd met [-Pmain=persons.MainKt].

    In de tekst van elk hoofdstuk staat vóór de resultaten van een programma het exacte commando waarmee het wordt uitgevoerd. We komen in hoofdstuk 3 op deze opzet terug.
